# Trusted Authorities

## Scope

This document owns FeedX-wide security and server-authority principles.
Domain documents identify which lifecycles use those principles without duplicating implementation details.

## Server Authority

Protected calculations and multi-write transitions execute in trusted database functions or Edge Functions.
Clients submit intent, display previews where useful, and refresh canonical read models from server results.
The server derives actors, validates state transitions, enforces scope, calculates protected values, and writes audit evidence.

Direct table CRUD is appropriate only where current RLS and domain contracts explicitly define it as the canonical mutation path.
Do not bypass an established lifecycle authority or add a parallel writer.
Retryable commands should use request identity and payload fingerprinting when supported.

## Row-Level Security

RLS is mandatory for exposed business tables.

Recruitment invitation tokens follow the public token authority pattern: only a random token hash is persisted, all Recruitment tables have RLS with direct anonymous/client table grants revoked, and narrow public RPCs revalidate token expiry, revocation, and opening state on every operation. Versioned candidate consent and Ready transitions are written server-side; a public hostname is never an authorization grant. See the People Recruitment domain contract.
Policies must align with the actual caller model:

- Admin access uses authenticated identity, permission, and outlet or record scope.
- Crew access uses validated opaque session tokens through token-bound authorities.
- Service-role use is limited to deliberately trusted server execution.

UI permission checks improve usability but do not replace RLS or in-authority validation.
Read policies must avoid leaking records, identities, private content, or cross-outlet state.

Platform's shared role, permission and outlet helpers own authorization execution cost as well as semantics. Their PL/pgSQL static queries reuse prepared execution plans; this is not a cache of role/permission results or a client/JWT authority replacement. Current Employee precedence, disabled-access denial, legacy-only fallback, permission aliases and outlet scope must remain unchanged. Verify complete authenticated read sets and allow/deny cases when optimizing these helpers; never remove RLS or completeness checks to improve latency.

## Security Definer Functions And Grants

Every `SECURITY DEFINER` authority must use a controlled `search_path` and schema-qualified objects where appropriate.
It must validate caller identity, permission, scope, state, and input before mutation.
Actor identity and trusted timestamps must be server-derived.

PostgreSQL grants are explicit:

- revoke default execution from `PUBLIC`;
- grant only to intended roles;
- keep internal helper functions non-executable by clients;
- avoid granting broad table writes that bypass the authority.

## Crew Token-Bound Authority

Crew access is separate from Admin Auth.
Opaque Crew tokens may cross an anonymous or authenticated transport boundary only into functions that validate the token and return the minimum safe payload.
Sensitive functions must recheck session expiry, Crew Access state, employee lifecycle eligibility, and record ownership.
Reset, disable, or security-sensitive changes should revoke prior sessions as defined by the domain.

Do not expose token hashes, passcode hashes, internal security state, or unrelated employee records.

### Crew Asset Presentation Details

`Manage Asset Details` is an independent Crew Special Access capability. Its
token-bound authority may change only an active outlet Asset's name,
description, location, and master-photo references. It cannot mutate quantity,
condition, category, maintenance, archival, or disposal. Photo variants are
written by the trusted `crew-asset-details` Edge Function and finalized through
the same request-id lifecycle/audit pattern as other Asset mutations.

## Admin Permission And Outlet Scope

Admin mutations require both the relevant permission and access to every affected outlet or record.
Where an operation spans an employee's home outlet and an operational outlet, validate every required scope explicitly.
Never trust a client-supplied actor, role, permission, or ownership field.

Employee role assignment and employee/Auth linkage use their canonical controlled paths.
Role configuration changes use the established trusted save authority.

Marketing adds explicit organization membership and role brand scope to the canonical Admin identity/action checks. Its business tables are RPC-only with direct browser grants revoked; private media is prepared and finalized through the same brand authority. Publishing claims/completions are service-only and revalidate the approving authorizer and pinned revision. See `../domains/marketing.md`.

## Immutable Evidence And Versions

Expected business revision conflicts exposed through PostgREST must use a non-retryable application error such as `PT409` (HTTP 409), not PostgreSQL engine serialization failure `40001`. The conflict still rejects the stale intent; callers reload and review canonical state rather than automatically resubmitting it. This distinction prevents transport-level transaction retry loops without weakening version checks.

Finalized business evidence is append-only or changed through an explicit reversal, correction, superseding version, or controlled reopen lifecycle.
Published content and schedules pin the versions consumed by downstream activity.
Historical snapshots preserve meaning when master data or rules later change.

Examples include financial period snapshots, roster publication revisions, SOP and learning versions, localized snapshots, performance evidence, stock and cash ledgers, and production traceability records.
Food Handling Compliance follows the same rule: evidence submissions and review decisions are append-only, replacements supersede only after verification, and private historical evidence is never overwritten by resubmission.
Employment Documents also follow this rule: Draft PDF evidence is replaceable, but Send pins the exact private object and server-calculated SHA-256 together with employee, legal-employer, issuer, and consent snapshots. V2 template contracts additionally pin the immutable published template version, contract-term snapshot, and canonical render-manifest hash. The server regenerates that manifest at Send and rejects a stale preview, so the server-rendered preview bytes are the bytes whose hash enters the existing immutable document authority. Viewed/Completed events are token-bound and append-only; withdrawal or supersession never edits the sent version.
The exact state model remains owned by each domain document and current contracts.

## Audit Discipline

Audit meaningful business and security actions, including protected state transitions, authority changes, immutable adjustments, and controlled reversals.
Store server-derived actor and time, relevant scope, prior/new state or reason where appropriate, and stable references to affected records.
Avoid recording secrets or unnecessary personal data.
Routine reads and cosmetic UI activity are not business audit events.

## Change Rules

### FeedX External Agent Gateway

`feedx_integrations.machine_identities` and `machine_credentials` are the shared FeedX External Agent Gateway identity and credential authority. Both are private, RLS-enabled server-only tables. A machine references an ordinary canonical Role Settings role, never an Employee or a fabricated Auth user. The database validates an opaque 256-bit credential's SHA-256 hash, activation time, expiry, revocation, enabled identity, active non-protected role and explicit permission grant on every request. Protected Owner/Admin bypass is intentionally unavailable to machines. Plaintext credentials are never persisted in the database, repository, logs or audit metadata. Identity registration remains a privileged operator action; no machine can create identities, issue credentials or edit roles.

An adapter must enforce its own fixed capability allowlist and redacted read projection after `feedx_integrations.authorize`. Machine role grants do not create a Supabase JWT, table grants or access to other RPCs. The retained `factory_mesti_inspection.view` code is the connection prerequisite; explicit navigation-module grants or preserved legacy grants authorize the bounded read tools. The Edge Function uses its internal anonymous key for token-gated business RPCs, not a service-role key; no Supabase credential is sent to an external agent. Role permission removal, role/identity disabling and credential revocation deny subsequent requests. Credentials expire after at most 180 days under adapter policy; the initial Staging QA credential has a 30-day lifetime. Renewal is explicit and may revoke the previous credential without changing identity or role. Identity/credential administration automatically appends safe before/after metadata to the canonical audit log, including revocation and credential replacement, with server-derived actor/time and no token or hash. MCP reads append bounded security access telemetry, never business evidence. No organization/company tenancy is inferred by this foundation.

The private `feedx_integrations.capabilities` registry owns business labels, workspace/module/resource, implementation availability, canonical Role Settings permission, transport binding, action and approval requirement. `view` means **View Records** and covers bounded List/Read/Search/Filter query operations. Create/Update/Submit/Complete/Verify/Approve/Cancel are separate action grants only for fixed, implemented Factory business transitions. The fixed adapter manifest is the executor allowlist; registry rows never create executable code.

Registration creates one dedicated ordinary role and a one-time expiring credential under adapter policy. Role Settings Create + Edit and canonical permission-delegation checks apply. Access changes require Edit, a dedicated role, canonical assignment authority, expected-state checks and the same role advisory lock as Role Settings. Module Select All/Clear uses the atomic `external_agents_set_capabilities` wrapper over that existing authority: any denial/stale grant rolls back the entire batch. Enable/disable preserves keys/grants. Keys remain expiring/revocable hashes; no employee impersonation or inferred organization ownership is used.

Gateway administration audit uses the existing audit log with server-controlled `trusted_external_agent` provenance. Authenticated clients cannot forge, edit or delete reserved `external_agent_*` / `external_machine_*` events or assert provenance. Earlier unverified management history is excluded. Resource telemetry remains service-only and records at most five registry-validated resource/operation pairs, without filters, search text, IDs, payloads or credentials. Administrator probes are distinguished from external requests; credential validity and a historical successful request do not prove a current Grok Bot connection.

### Factory operational actions

`config/factoryAgentActions.json` and private `factory_actions` bind each supported action to its business module, canonical human operation, target, accepted intent fields and confirmation requirement. `factory_agent_action_<domain>.<action>` grants are machine-only; they never follow from View or appear in the Human Role Matrix. Execution requires the connection prerequisite, exact action and corresponding module View grant. Existing Factory-wide scope remains unchanged; no company/outlet tenancy is invented.

The Gateway uses anonymous, token-gated `factory_agent_action_context` / `factory_agent_execute_action`, never service-role business writes. Existing human RPC signatures delegate to the same private business bodies with an explicit human-or-machine principal. Machines have no Employee/Auth identity. Physical Production operator evidence remains human-owned. Calibration records require exactly one human or machine recording principal; other machine mutations retain stable identity in their immutable receipt and trusted audit event rather than fabricating an Employee.

Planning/draft actions and supported pre-start/draft cancellations may execute autonomously. Server-owned execution policy distinguishes autonomous, conditional and human approval. Independent Production/Receiving record verification may execute without a second human gate when completion has canonical Human attribution or a Human-confirmed, source-version-matching Agent receipt. Independent Product/Raw Stock Check approval additionally requires every item counted and zero variance. Missing attestation, variance or changed evidence retains exact-intent Human review. Area/Equipment Cleaning Complete/Verify execute directly under their respective grants, including same-actor Complete → Verify, without a mandatory Action Request. Genuine work/inspection, required record fields, lifecycle, source binding and audit remain required; an Agent instruction is never physical evidence. Other physical inspection, QC measurements, completion and count submission do not become autonomous through a capability grant. Those actions require an authorized human to confirm the exact intent and evidence reference in AI Integrations; this is not proof fabricated by the Agent. Confirmation is source-version bound, expires after 30 minutes, and does not execute the command. The Agent retries the same request after confirmation. The current dispatcher requires a live opaque Agent credential on every execution and has no approved credential-free worker/continuation contract; confirmation therefore retains Awaiting Agent Execution with a copyable exact retry command instead of storing credentials or silently impersonating the Agent. Conditional execution reuses all canonical source/lifecycle, scope and independent-identity checks. Human business authority and applicable independent-review rules are rechecked. No machine can issue its own confirmation.

Requests/receipts are private and keyed by stable machine identity plus request UUID. Identical retries return the committed receipt; changed payloads cannot reuse a key. Canonical inner retry keys are identity-namespaced. Role locking, target/child-evidence versions and canonical inventory/lifecycle locks protect concurrent execution. Outside Area/Equipment Cleaning, an Agent cannot verify/approve its own prohibited prior work, including linked Production Job Order work; replacing a credential does not replace identity. Failed validation rolls back the whole operation. A lost response is an unknown outcome recovered only with the same request ID. Committed action receipts survive a later telemetry failure because their trusted business audit already committed atomically.

Access remains staged through the existing selector/review/confirmation contract. Grant state, pending changes and execution requirements are presented independently. Action Requests is an exception/continuation queue. The existing identity-bound, Factory-permission-redacted read authority derives Pending Human Approval, Awaiting Agent Execution and Needs Resolution from the saved intent, current policy, source version and confirmation validity. Source changes block approval/continuation with a specific reason and a new-intent recovery action. Historical pending intents whose policy is now autonomous are Legacy Pending Request evidence under Activity, not new work or mandatory retries. Completed receipts and expired approvals also appear only in Activity/request history; definitive denials remain Activity events, never fabricated request rows. The projection never executes, approves, deletes or migrates requests and never combines distinct IDs/source versions. Open work is not displaced by the latest 50 completed receipts. It refreshes through one visible-tab read loop (30 seconds and focus recovery), coalescing concurrent reads; confirmation expiry is a display of the existing 30-minute validity, not a new persisted lifecycle. Rejected attempts remain in Activity rather than being fabricated as request rows. Activity distinguishes action eligibility checks and successful request processing from completed business work; RPC success must never label a pending intent as a completed Factory action. Action requirements and View dependencies are explicit, never automatically granted. Action-request payload inspection and confirmation require corresponding Factory authority in addition to Agent management. Cleaning Verify retains its shared lifecycle/result validator in canonical Human/Machine writes and Gateway preflight. Ordinary autonomous success creates a completed receipt rather than pending work; definitive permission/lifecycle denials roll back without creating a request. Historical invalid requests remain preserved as legacy evidence, never automatically promoted or executed. Context and privacy-safe transport errors explain the required completion. Unsupported transitions remain unregistered; no generic SQL/table writer or arbitrary RPC dispatcher exists.

AI Integrations Activity is a business-oriented display of the existing authorized Admin Activity and saved-request responses, not another audit authority. A Completed mutation requires a matching canonical completed receipt bound to the Agent identity, request, action and source version. Exact duplicate retry evidence may share one entry only when request/intent/source identity matches; distinct requests and uncorrelated events remain separate regardless of timestamp. Reads, committed changes, denials/failures, configuration changes and pending execution have different outcomes. Technical eligibility/API events remain individually inspectable in diagnostics and never prove business completion. Targets and operation evidence retain the existing Agent-management and Factory permission boundary; read-only administrators retain their existing safe Activity visibility. Canonical Factory module links do not invent unsupported record deep links. Date/module/outcome filters and pagination cover the returned source windows (50 access events, 50 configuration events, 50 completed receipts plus saved open requests); older canonical history is neither deleted nor reconstructed. Historical record names, result counts and missing correlations are not inferred.

## Native Assistant Text Authority (Staging Phase 1A)

### Realtime voice evaluation

Canonical Staging gates OpenAI WebRTC and Grok Voice WebSocket behind separate provider credentials, approval references and existing Role Settings edit authority. The browser gets the OpenAI SDP answer or a 60-second Grok connection token. The isolated HUD receives state updates only. The text credential is never a fallback.

Before negotiating, the service reserves a call against the active Admin and their owned, current-scope conversation. One active reservation per Admin, eight attempts during the evaluation and six inventory reads per call limit evaluation access. Both providers can request only the fixed Finished Goods read through this application. The tool rechecks the current human Admin permission and calls the canonical reader, which returns scope, read time and source. A model function request grants no authority. No voice execution is written to the Operations Network.

The browser closes a call after three minutes or twelve user turns, or when hidden. These client limits and the Grok token expiry do not impose a provider-side spending cap or terminate sessions opened outside the app. Use dedicated evaluation credentials with provider limits.
