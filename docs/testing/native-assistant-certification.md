# Native Assistant Staging certification

Run the existing contract and orchestration gate with `npm run test:assistant-business`. It verifies implemented capability behavior under fixtures and ensures certification scenarios still correspond to module-owned READ contracts.

Regenerate the module and operation matrix with `node scripts/assistantBusinessMatrix.mjs`. Its inventory comes from the Admin module projection, the reviewed module coverage and the current shared READ bindings. Update the owning coverage declaration when adding a module. A registered query must be discoverable by its business label and retain its authorization and completeness semantics. Contract and deterministic SDK results remain separate from authenticated answers.

`node scripts/assistantBusinessMatrix.mjs --catalog` emits the machine-readable business catalog from those same sources. Each operation links to its canonical owner, scope, query dimensions and completeness contract. Richer domain declarations name their entities, relationships, time basis and metrics with evidence fields and units. A null semantic declaration means the owner supplies only its existing operation contract. The export describes implementation coverage. Text and Voice discovery filter the operations against the signed-in user's current access.

`npm run verify:assistant-interfaces` checks canonical module ownership, reviewed source files, capability schemas, coverage restrictions and linked certification scenarios. It also checks SQL definitions and grants for named public RPCs selected through a domain helper or register selector. Every registered READ requires at least one specific final-answer scenario. A reviewed coverage or source update triggers the drift check. Recording a baseline does not certify an authenticated answer. A read-only Staging policy snapshot can be supplied to the matrix generator with `{as_of, enabled}`, where `enabled` is the list of enabled operation IDs.

Review the [business acceptance matrix](../audits/native-assistant-business-acceptance-matrix.md) and [scenario definitions](../../qa/staging/nativeAssistantCertification.mjs) before starting the live run. In an authorized canonical Staging account, establish the expected result from the domain-owned source, record scope and time, then ask the scenario through Native Assistant Text. Submit follow-ups in the same conversation. For isolated scopes use existing test accounts and permissions. Record any disabled capability, blocked scope, missing fixture, or active request budget as BLOCKED.

Record the canonical deployment SHA and the actual saved turn identity, user-facing reply, model, completion state, tool state and evidence. Export only the reviewed fields through an authorized read path. Do not record provider secrets or private employee records. Store the run outside Git. The JSON maps scenario IDs to `{turn, source}` or `{blocker}`. Each scenario defines the fields expected in its independently obtained source result.

For rejected READ arguments, compare the offered operation schema with the domain's rules for combinations of fields. Correction events may include declared field names, a validation reason, and fixed expected values from the contract. They omit submitted values and are excluded from saved business evidence. A deterministic retry should verify that the invalid call never reaches the source and the corrected call produces evidence with the original scope.

For source-validated filters, a correction can follow an authorized read without yielding business evidence. Factory stock unit checks distinguish an unrecorded unit from a valid unit with zero matches under the other filters. Mixed questions should expose a matching authorized operation for each clause before checking the saved final answer.

For an explicit unfiltered Finished Goods SKU page, the model selects the read and the Assistant can render the bounded page directly from saved evidence. Compare the catalogue total separately from the page size and check every returned SKU, balance and unit. A follow-up must match the prior complete page scope. Record a model-assisted read separately from a provider-free direct read.

Run `npm run qa:staging:assistant-certify -- /absolute/path/to/run.json --strict`. It requires the expected capabilities, matches declared scope and evidence, and checks whether the answer includes required facts. The exit code fails on FAIL and, with `--strict`, also on BLOCKED. A missing scenario cannot pass. The command evaluates the supplied saved records and does not send provider requests. Review any answer claims outside the script's targeted checks manually.

For source-derived cases, save independently read, authorized source rows outside Git. The input groups are `assets`, `inventory`, `movements`, `finishedGoods`, `productGroups`, `departments`, `positions`, `leave`, `plans` and `finance`. Use the source projections consumed by `generateSourceCases`. Count entries carry an expected `count` and exact `filters`. Outlet and Brand questions also carry the applicable display name, and Finance carries both expected monthly records. Generate cases with `npm run qa:staging:assistant-certify -- --generate /absolute/path/to/source.json`. Templates include English, Malay and Chinese asset and inventory prompts, named multi-outlet counts and an asset follow-up. Submit the cases through the existing authenticated Assistant within its normal daily budget. Attach the genuine saved `turn` to each case and preserve array order. Run `npm run qa:staging:assistant-certify -- --generated-run /absolute/path/to/cases.json --strict`. A follow-up must share the preceding passing turn's session and occur after that turn. Mark an exhausted allowance or missing authorized source as BLOCKED. Project-level source readings can seed candidate cases and still require a human-scoped comparison for live certification.

For a full release record, identify which operation lacks authenticated end-to-end evidence and why. Keep historical passes identifiable by turn/time and release, and leave new or changed scenarios pending until observed. Scripted provider, replay, owner-session and microphone evidence are distinct. Never toggle a live policy or bypass a request budget to obtain a passing record.

Managed knowledge scenarios compare the saved citation's document identity, version, publication state, section, source scope and excerpt with an independently reviewed canonical record. For mixed questions the scenario also requires evidence from the separate business READ. For each source, use an existing published example and record any missing publication or policy as BLOCKED. State-change controls such as revoke, future dates and scope denial belong in the deterministic gate when an authorized disposable Staging fixture or restricted account is unavailable. See the [knowledge source inventory](../audits/native-assistant-knowledge-inventory.md).

The Asset Tracking reliability run verifies a fresh Text conversation, an explicit Text correction in the existing failed Voice conversation, and a follow-up at the confirmed outlet. Obtain the current Asset Tracking quantity independently, use the saved turn and confirm the dispatcher outcome, source, resolved outlet, exact record and reported amount. A saved failed Voice turn can be used to certify Text recovery without starting Voice. SDK parity, injected source failures and restricted access fixtures remain separate from authenticated browser checks.

## Independent operational answers

The [operation-specific cases](../../qa/staging/nativeAssistantOperationalCases.mjs) identify the record identity, business fields and units for each operational question. The [filtered register and closing cases](../../qa/staging/nativeAssistantRegisterCertification.mjs) cover exact counts and separate Restaurant stock-check publication from Finance valuation. Findings from a module owner's source must be captured independently of the Assistant's evidence.

1. Use the existing authorized Staging account to open the owning Admin view or call the same authenticated domain read from that view. Choose a real outlet, employee, brand or other scope available to that account. Capture the same filters, period, sort and page that the question requests. Use a consistent pseudonymous actor reference to link this capture to the submitted turn.
2. Record the current page, observable next-page boundary, and only the required identities, expected fields and units. For a summary, record the owning service's scoped summary. For a count, use the owner’s exact filtered count or enumerate the entire authorized filtered set. A page length cannot establish a population count. Capture on either side of the turn if records may have changed and resolve differences before attributing a failure.
3. Supply these expectations in the existing source generator under `operationalAnswers` or `registerAnswers`. Each operational entry includes `operation`, a human-readable `scope_label`, normalized request `scope`, `records`, and, for a page, `has_more`. A register entry instead supplies `scenario` (for example `read_sales_records_filtered_register_count`), `scope_label`, `scope` and the expected `count`. Preserve the outlet, calendar period and exact channel filters for recorded sales input. The question must not include internal UUIDs.
4. Each entry also includes `capture` with `environment: "staging"`, `method: "admin_view"` or `"domain_service"`, the canonical `module_id`, the owner's Admin route or RPC in `authority`, `actor_ref` and the timestamp `at`. Use a route only for a read actually observed in that module. Project-admin SQL, prior Assistant answers and copied snapshots of Assistant tool evidence do not establish the same end-user authority. Keep snapshots of employee-specific reads local and use only the contracted metadata fields.
5. Submit generated questions through the authorized browser, retaining the genuine request ID, conversation ID, completion state, final answer, evidence, model and ledger usage. Attach `turn.actor_ref` from that actor and run the existing `--generated-run` evaluator. It checks tool selection, scope, source/time, page boundaries, evidence values and the specific claims in the answer. A successful tool call and an answer without the requested measurements cannot pass this check. Human review covers additional assertions or wording outside the targeted checks.

For a verified empty page, record `expectation: "empty_page"`, the empty independent page and its boundary. For an access boundary, record `expectation: "denied"` or `"disabled"` and a sanitized server trace tied to the same session, turn, operation and denial code. Do not simulate a denial by changing Staging permissions. A missing owner capture, policy-disabled positive case, unavailable live account or exhausted Text budget stays **BLOCKED**. A mismatched source or final answer stays **FAIL**.

For the Restaurant closing case, compare the submitted audit's current published revision, count date and coverage with the owner’s publication. A missing audit and an existing unpublished audit are distinct results. For Finance, capture the raw monthly Reporting `closing_stock_evidence` and outlet/period. A complete published zero, a partly valued publication and an unavailable valuation produce different expected answers. An empty Staging publication register can certify the unavailable case only.

Keep three results separate in release reporting: deterministic fixtures and source replays, authenticated saved Text turns with their execution path and measured tokens, and actual human-microphone Voice sessions. Scenario coverage counts describe the questions the suite can verify.

Filtered count captures record the business grain as well as the total. Task review queues count assignments, Crew onboarding counts scoped members including those without an enrollment, and Payroll counts periods independently of run revisions. For source-paged Factory label, transfer and cash counts include the independently read first-page IDs. The Ads case counts exact-period reporting snapshots. The WhatsApp workflow service exposes at most its latest 100 definitions; at the ceiling the true population is unavailable. Brand-wide consent totals and scoped customer counts require separate source values.

Mutable operational evidence needs a contemporary comparison. Capture the authorized owner result within 15 minutes of the saved evidence; the saved evidence must also come from the turn being certified. An older capture is BLOCKED even when the numbers happen to match. Re-read the same authorized scope to resolve this gap.

For complete RPC collections a long row can reduce the returned page size from 20 to 10, 5 or 1. The evidence records the original request, the actual page and size, the matching total and the next-page boundary. Compare the same starting offset and continue using the returned coordinates. The first 2,000 matching records remain addressable. A single record or essential metadata exceeding the 10 kB evidence limit is unavailable through Assistant; inspect it through the authorized module. This size adjustment neither re-runs the owner read nor calls the model. A later insert, deletion or sort-key update can still change the contents of offset-based pages.


The module matrix separates the human permission and documented source limits from UI fields that a reviewed Assistant projection omits. Each registered READ contributes its actual source or RPC, scoped population, and any document publication/version condition. The field-restrictions column records intentional privacy omissions separately from missing source data. A UI-only finding cites the specific human UI and READ implementation, including the owning READ for shared modules. An exclusion can protect sensitive data. Other dimensions stay undetermined until a source comparison establishes their status. Adding a scenario changes the test inventory; a recorded source-backed browser outcome is needed to change live acceptance.

### Operational workflow guidance

The existing system-guidance tool searches reviewed release passages from canonical domain documents. Each citation pins its document, section and passage revision. Release passages describe rules. A current balance, actual transition, private SOP or confirmed cause requires the corresponding authorized live source. Human permissions and existing per-capability policy are rechecked by the dispatcher. The Assistant user guide remains independently available.

The build verifies every mapped passage against its source section and fails on domain-document or tracked service drift until reviewed. Check an independently selected passage, a scoped live READ and the final conclusion separately for a mixed investigation. Provider-free Text/SDK tests establish tool handling and evidence retention. A model-assisted conclusion and real microphone interaction require separately recorded acceptance.
