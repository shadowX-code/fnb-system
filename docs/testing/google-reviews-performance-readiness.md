## Recovered model

Positive = 4–5 stars, neutral = 3, negative = 1–2. Quality denominator includes all eligible monthly reviews, including neutral. Positive component is `min(positive / approved monthly outlet target, 1) × 15`.

| Monthly negative rate | Quality points |
| --- | ---: |
| ≤2% | 5 |
| >2% to 5% | 4 |
| >5% to 10% | 3 |
| >10% to 15% | 2 |
| >15% to 20% | 1 |
| >20% | 0 |

These bands already exist in the canonical domain contract and dormant adapter; no thresholds were invented. Missing/invalid target, incomplete evidence or zero eligible reviews remains Pending, never zero or an assumed five Quality points. The score is shared by eligible employees in the same outlet/month.

## Minimum durable Performance result reassessment — 2 November 2026

This reassessment narrows the earlier retention question. A FeedX-calculated score is not literally a field returned by Google. The public policies reviewed do not expressly classify a score-only employee Performance outcome as stored API Content, and they do not expressly exempt it. The earlier absence-of-permission finding must not be presented as an explicit prohibition on every derived numeric outcome.

The [Business Profile third-party policies, Insights section](https://support.google.com/business/answer/7353941?hl=en) permit combined aggregate performance reporting when Business Profile-specific data is also separately accessible. This qualifies any blanket assertion that Google prohibits all aggregation. That reporting provision does not specify whether review-derived employee scoring falls within its scope, or authorize indefinite retention after source-cache expiry, disconnection or API termination.

The [GBP API Content storage policy](https://developers.google.com/my-business/content/policies) defines Content as content provided through the APIs, limits stored Content to temporary storage of at most 30 calendar days, and prohibits manipulating or aggregating stored Content. [General API terms, sections 5(e) and 8(b)](https://developers.google.com/terms) restrict permanent copies and derivative works of API content and require deletion of permitted cached/stored content on termination. Neither provision resolves the classification of a non-reconstructable numeric FeedX outcome. The [User Data Policy](https://developers.google.com/terms/api-services-user-data-policy) recognizes derived data and, in its conditional Limited Use rules, internal aggregate operations; that human-access exception is not a permanent-retention exemption. Its secondary-use disclosure requirements remain applicable independently of storage minimization.

The minimum technical proposal reuses the existing Performance result, not a monthly Google dataset:

| Field | Minimum treatment |
| --- | --- |
| Employee, outlet, month | Existing verified People/Performance identity and scope |
| Customer `/20`, official total | Only required numeric business outcome; retention classification remains unresolved |
| Target audit revision, formula revision, finalization actor/time | FeedX configuration and decision audit; no copied Google content |
| Text, reviewer identity/photo, review IDs, individual ratings | Excluded from Performance |
| Monthly counts/rates/distribution, source-content hashes or copied review snapshots | Excluded from this minimum durable proposal |

Removing review data materially reduces the proposed storage, but naming the resulting score FeedX-owned does not establish a policy exemption. Storing only the combined official total would still embed the Google-derived contribution and lose the required five-dimension auditability; it does not resolve the interpretation.

**Decision:** no compliant durable scoring path has been established from the public terms. This is an unresolved applicability question, not a verified categorical ban on score-only retention. The exact outstanding determination is whether a month-end, outlet-shared employee Customer score and resulting official total, retained with FeedX-only configuration/decision metadata and no Google source dataset, are outside the API Content retention restrictions, and what deletion obligations remain. No Google contact or clarification workflow was initiated.

Code inspection confirms the existing result schema can hold Customer and total scores; the current finalizer deliberately rejects Customer-pending periods, and refresh returns existing finalized rows without recalculation. No scorer, preview, migration, server guard or application behavior was changed. No employee score or target was mutated, and nothing was deployed. Existing synthetic/rolled-back verification remains applicable to unchanged code; month-end Customer finalization is **not operational** and was not represented as newly tested. This documentation-only reassessment requires `git diff --check`, not another preview or full QA cycle.
