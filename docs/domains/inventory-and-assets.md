# Inventory And Assets

## Purpose And Scope

This domain owns restaurant inventory state, controlled movements and reconciliation, recipe/usage relationships used for stock operations, and physical asset lifecycle management.

## Canonical Ownership

Current inventory and asset services, lifecycle RPCs, migrations, RLS, and tests are authoritative.
Factory raw material and finished-goods stock belong to `factory-warehouse.md`.
Factory recipes and BOM belong to `factory-master-data.md`.

## Core Entities

- Restaurant inventory items, locations, balances, and movement evidence
- Receipts, issues, transfers, adjustments, and stock checks
- Reconciliation periods, requests, and canonical stock projections
- Restaurant recipes and usage mappings that affect inventory interpretation
- Assets, assignments or location state, lifecycle events, and audit history

## Lifecycle And Business Rules

Stock changes occur through established lifecycle authorities that validate scope, quantities, state, and retry identity.
The canonical balance is server-derived from accepted evidence or the established read model; the browser must not manufacture final stock.
The Inventory Dashboard is an outlet-scoped read-only overview of Stock Check evidence, order activity, and standard cost. The existing `inventory_dashboard_stock_evidence` projection reports Below Par or Sufficient at the last verified count, Changed Since Check when a relevant movement follows the count, and Unverified when the count or its sequence is unusable. Live inventory value remains outside that projection. Check completion uses today's scheduled groups. Operational Activity shows current due runs, the latest missed run per active group over the prior seven Kuala Lumpur business dates, and the latest five recorded movements in the selected outlet scope. The existing Closing Approval context supplies publication for the most recent ended Closing Month when the user can view the corresponding Stock Check evidence.

The Dashboard cost read, `inventory_dashboard_cost_insights`, requires Dashboard access, existing standard cost permission and access to every requested outlet. The 30-day Malaysia business-date window counts each actively linked global inventory item once. It compares effective standard costs per item through the last effective revision in the window. The opening basis is the last cost before the window, including an undated configured baseline when applicable, or the first dated cost in the window when it has a later comparable revision. Superseded revisions do not enter the comparison. Explicit zero is configured, and the Top 5 ranks absolute RM change per unit. The read derives from the existing revisions. It owns neither purchase-price analytics nor a second cost projection. An incomplete operations read blocks its aggregates, while restricted or unavailable cost and closing reads have independent states. Scope changes hide data from the prior scope.
Corrections use explicit adjustments or controlled reversal behavior rather than rewriting posted history.

Restaurant Stock Check drafts (scheduled and audit) are saved through `inventory_save_stock_check`; a submitted check and its item evidence are immutable. The server owns request idempotency, outlet/group validation, creation and submission timestamps and actors, and a completed scheduled check's group timestamp. Audit draft deletion uses `inventory_delete_stock_check_draft` and records server audit evidence. Stock Check completion records a count; it does not itself post an inventory movement or adjust a balance. The shared Stock Check authority accepts the server-derived actor from the Admin Auth or opaque Crew session wrapper, which enforces the applicable capability and outlet scope. Existing historical rows remain readable.

The Audit Stock Check Result pins the canonical Master Inventory unit cost into each item evidence row at submission, only when a cost was explicitly configured and the item's count UOM matches the cost UOM. This read-only snapshot supports Stock Value (`Actual × unit cost`) and signed Variance Value (`(Actual − Par) × unit cost`) without changing inventory movement authority. Audit shortage/excess display and quantity variance likewise derive from the immutable Actual and Par counts, rather than assuming that all historical Admin/Crew evidence used the same stored variance sign. Earlier submitted results have no recoverable historical cost snapshot; missing, default-unconfirmed, or unit-mismatched costs display `—`, never an invented RM0. Audit Detail displays Known Stock Value as a partial, physical-count subtotal when some lines are unvalued, with valued item coverage and a missing pinned-cost count. The Unvalued filter isolates unavailable stock line values and leaves the subtotal and coverage intact. Shortage Value, Excess Value and signed Net Variance use counted rows with a recorded unit, valid Par and pinned cost. Each is marked Partial when any row is ineligible, with independent variance coverage. The totals stay based on the full audit regardless of filters. Approved Closing Stock comes exclusively from Closing Approval.

Admin Start Audit and Crew Continue create the server draft before counting. The read-only MYT Count Started At and Count Submitted At come from the existing `created_at` and `submitted_at` lifecycle fields. Draft saves, resume and retries retain the original start. New audits derive the business date and automatic name at creation. Month-End Closing names include the selected Closing Month. Existing audit timestamps, business dates and custom names are retained. Admin audit category, item search and count status filters affect the visible rows only. Progress and completion use the full roster. The Stock Check read model shows absent actual quantities as Pending with no variance. Explicit zero is counted and uses the existing variance rules.

Submitted Audit Stock Checks can be corrected through a linked Audit Stock Check draft. Admin users need Stock Check view, edit and submit permissions in the audit's outlet. Crew maintains its ordinary count permissions and can read submitted correction evidence. The server copies the original count date, audit and item notes, closing metadata, item roster, UOMs, Par and pinned costs. Corrections save through the existing Stock Check command, accept individual quantities and item notes, and require a reason and a changed item at submission. The correction's own created and submitted timestamps record the correction work. A correction never moves stock or reprices the original count. Historical audits remain readable. A closing without the required frozen roster and pinned costs needs a new complete count.

Each submitted audit can have one successor. A draft can be continued or discarded. A submitted correction is the current evidence in its chain, and previous versions stay readable with their original evidence. Inventory Dashboard evaluates the current evidence using the original count timestamp when comparing stock movements. Closing Approval blocks the source of a pending draft or submitted successor. The latest submitted closing correction is eligible for initial approval or the existing reasoned publication revision, as applicable. An earlier or later physical count still requires item-level reconciliation, and cutoff validation uses the original count's submission time. A pending or submitted audit correction never changes an existing published valuation.

Month-End Closing uses the existing Admin and Crew Audit Stock Check workflow. Counters select the Closing Month (the accounting period) without entering a physical cutoff. The shared Stock Check authority freezes the roster of active outlet-linked items at submission and requires one explicit count per item, including zero. Closing evidence excludes skips, duplicate items and Par defaults. Admin and Crew may save temporary item skips in drafts. Both offer Stock In Use, Cannot Access, Pending Verification, Item Not Found, and Other with a required explanation. The chosen reason uses the existing item skip evidence field. Skipped items have no actual quantity and must be undone and counted before submitting a closing. Scheduled and other audits retain the existing item-skip rules. Legacy closings without the necessary roster or cost evidence remain readable. Audit Detail explains the eligibility issue and lets Admin users with Stock Check submit permission open a fresh closing setup. Setup reuses the recorded Closing Month when available and leaves it blank otherwise.

Audit Result shows the recorded Closing Month and one Closing Stock status, with blockers and the Review Closing action. Audit history and operational timestamps are available on demand. Confirm Closing publishes to the existing Outlet P&L read for the matching outlet and month. Closing approval is an Admin action requiring Stock Check view, `inventory_stock_check.approve` and access to the audit's outlet. The accounting cutoff is midnight Malaysia time at the start of the next month. Approval opens after that cutoff. The approver confirms the physical count cutoff in Malaysia time from the actual count evidence before first publication. It must be on or before Count Submitted At. Operational start and submission times do not establish physical or accounting cutoff evidence. Existing cutoff evidence recorded on historical audits stays intact and can be used during approval. An approved cutoff is stored with its immutable closing revision. A confirmed physical count at the accounting cutoff uses the submitted actuals. For an earlier or later count, the approver confirms the month-end quantity in the count unit and records supporting evidence for every item, including unchanged quantities. The movement ledger is outside this calculation. The approved amount is the sum of these quantities multiplied by the configured unit costs pinned at submission, rounded to sen after summation.

Inventory owns the append-only closing revisions. The approval command serializes each outlet and accounting month, records the audit, both cutoffs, approver and request, and publishes the first revision or an explicitly reasoned successor to the current revision. The source audit and prior revisions retain their evidence. Reporting consumes the current publication only.

Stock Check Groups is an outlet-scoped configuration surface; due/completed state and last-check evidence belong to Stock Check execution. Its verified read snapshot is keyed to Auth/outlet scope: a new scope cannot display or act on previous-scope rows while its read is pending, while same-scope refresh may retain verified rows. Group status stores `active`, `inactive`, or `archived`. The existing quick deactivation writes `inactive`, not `archived`; explicit archived/reactivated status changes currently use the Group edit form. No separate restore lifecycle command exists.

The Crew Inventory read projections remain token/outlet-scoped and side-effect free. The mobile catalog exposes the canonical active inventory item's `photo_url` for recognition thumbnails; Stock Check summaries expose their persisted `updated_at` and first counted `cover_item_id` for compact draft presentation. These are read-only display fields, not new item-image or Stock Check authorities.

Asset creation and lifecycle transitions use the existing asset authorities.
Status, location, assignment, and retirement history must remain traceable.
Inventory and asset records are related operational concerns but retain their own entity lifecycles.

### Asset Tracking Application Read Boundary

`assetTrackingService` remains the approved Asset Tracking application boundary for Supabase reads and lifecycle RPC intent. `loadOutletTrackingData` owns the concurrent five-collection list/summary/activity read set; its consumers must not recreate a divergent route-level query bundle. Imports use `asset_import_row`; the browser must not create an independent movement-log import path.

Asset availability and physical condition are separate canonical projections. Availability is derived from quantity and the configured minimum as **Available**, **Low Quantity**, or **Missing**; zero quantity is **Missing**, never also Low Quantity. Physical condition remains **Good**, **Needs Attention**, **Under Maintenance**, **Damaged** (legacy-compatible), or **Disposed**. The shared Asset read-model selector is the sole source for availability, condition, summary counts, quick filters, and list presentation, preventing filter/count drift. It also supplies the semantic activity labels for imported, adjusted, inspected, maintained, and archived assets. Maintenance eligibility is derived from the category setting plus the per-asset `maintenance_override`; Admin editor entry points share the same form state and validation rules.

Native Assistant Asset Tracking uses `asset_tracking.view` and rechecks the authorized outlet for each read. It returns current non-archived asset record counts and stable name/ID pages of recorded quantities. Exact name or code identifies one asset. Movement history reads the same `asset_movement_logs` used by Asset Tracking and returns recorded movement dates, before/change/after quantities and units for the selected asset. A date range is inclusive and pages retain the confirmed outlet, asset and date filters. A matched asset with no movements is distinct from an unresolved or ambiguous asset.

Native Assistant Master Inventory uses `inventory_master.view` and the same item-to-outlet links as the Admin catalogue. Filters apply to both exact counts and list pages. One outlet can resolve an exact item name or SKU. A linked item can appear in multiple outlet counts, while a distinct scoped total counts it once. Inventory Movements uses `inventory_movements.view` with its own outlet and recorded date, type, item and reference filters. Counts measure movement records and preserve recorded quantity and unit per row.

Inventory Dashboard stock evidence is a separate read under `inventory_dashboard.view`. It covers active positive-par positions and retains check date and source freshness. Only a sufficient or below-par position asserts a usable count. A changed, unverified or missing position does not supply current on-hand stock.

Inspection item and evidence reads are constrained to inspection headers already returned under the current outlet/RLS scope. Actor display lookup is a limited Asset service projection; it is not a page-level employee-directory query. Direct Admin condition edits remain a deployed compatibility boundary; inspection draft persistence and archival use their scoped server-authoritative lifecycle paths.

Asset lifecycle history is append-only for ordinary clients: assets are archived rather than deleted, and movement, maintenance, inspection, item, and evidence rows are written only by trusted lifecycle authorities. Draft inspections may be resumed or archived through their canonical RPC; finalized inspection headers, items, and evidence are immutable. Database triggers enforce asset/outlet consistency for lifecycle children, and each successful lifecycle request records server-derived audit evidence in the same transaction.

Asset imports may update only an unambiguous same-outlet match: asset code is the preferred identity, while duplicate name-only matches are rejected for explicit resolution. Asset master photos normalize supported camera/library sources (including iPhone HEIC/HEIF where the browser can decode them) into cache-versioned source, 1200x900 display, and 400x300 thumbnail variants, requesting WebP and retaining the actual safe browser encoding (WebP, PNG, or JPEG) and matching content type/extension when the browser falls back. Crew Asset create, initial-photo, and details Edge Functions accept the same formats; photo-format handling does not alter Asset capability, outlet scope, or update authority. The display variants use an EXIF-aware, user-selected 4:3 framing transform; they do not alter asset content. The shared Admin/Crew crop preview uses the same cover/zoom/overflow geometry as the saved variants. Detail and reopened Edit display the saved 4:3 image without another crop; thumbnails retain that framing at a smaller size. Crew and Admin render thumbnail -> display -> source -> Asset icon. Photo replacement stages the entire new bundle, persists its references, then best-effort removes the prior bundle; a failed record save cannot delete the currently referenced photo. Inspection evidence remains immutable single-source evidence and is never normalized through the master-photo pipeline.

The optional-field query fallbacks in the Asset service remain intentional compatibility debt until every supported environment is proven to have the corresponding deployed schema. They must stay contained in the service; no page-level fallback or legacy-field branching is permitted.

### Crew Mobile Asset Execution

Restaurant Asset Tracking remains the only asset source of truth. Crew Mobile receives a minimum-safe, token-bound outlet projection through `crew_asset_mobile`; it never receives direct table access or Admin cost, supplier, purchase, or unrestricted audit metadata. `Add Assets`, `Adjust Assets`, and `Perform Asset Inspections` are independent per-account Crew Access capabilities. Any one capability permits the Assets read surface, while each mutation authority verifies its own capability again on the server.

Crew additions create one active, outlet-derived canonical asset with active-category validation, a server-set initial condition, Crew creator attribution, lifecycle idempotency, and audit evidence. Admin and Crew creation share the same field semantics: name, active category, initial quantity, and the canonical Asset unit vocabulary are required; photo, asset code, the existing free-text Asset location, and description are optional. New creation always stores minimum quantity as zero; minimum quantity and operational remark remain post-create/Admin concerns so historical values stay compatible without duplicating description. A no-photo creation uses the standard lifecycle RPC. A photo-inclusive Crew creation stages its media bundle under one request identity and commits the Asset plus all three photo references through one server transaction; any known upload/finalization failure cleans staging and leaves no visible Asset. A same-request replay returns the original result without duplicate Asset or media records. `Manage Asset Details` is an independent Crew capability for name, description, location, and master-photo presentation only; it cannot alter quantity, condition, category, maintenance, or lifecycle. Direct Crew adjustments change quantity only and preserve physical condition. Crew inspections remain the canonical reconciliation path: they record expected and counted quantities, condition and evidence, and atomically create a movement only when the count differs. A Crew member may cancel only their own resumable inspection draft through the token-bound archive authority; it records an immutable lifecycle event while completed inspections, evidence, and Asset state remain untouched. Draft saves do not upload photo evidence, so cancelling a draft leaves no draft-only Storage object. The Crew Activity view is a read-only, outlet-scoped projection of canonical movements and completed inspections, not a separate event source. Crew cannot manage maintenance, disposal, archival, categories, imports, or exports.

Inspection drafts are owned by the current Crew employee and outlet. Completion atomically writes canonical item/evidence rows, quantity corrections, condition, last-inspection state, activity, and audit. Required evidence uploads are mediated by the token-bound `crew-asset-evidence` Edge Function; the Crew browser receives no Storage write authority. Task-to-Asset deep linking is deliberately deferred until Tasks defines a canonical Asset evidence reference contract.

Admin access requires inventory or asset permissions and outlet/record scope.
Protected mutation functions validate the actor server-side and expose only intended grants.
Posted movements, stock-check outcomes, lifecycle requests, and asset transitions retain immutable or append-only evidence as defined by current contracts.

## Workflows And Integrations

Admins configure items and locations, record operational movement intent, perform stock checks, reconcile differences, and manage assets. Specially authorized Crew may view its current outlet assets, add an outlet-scoped asset, record operational quantity adjustments, and execute canonical inspections from Crew Mobile; these actions remain visible to Admin with Crew actor attribution.
Purchasing can supply receipt context but does not own stock posting.
Restaurant finance may consume valuation or usage projections without taking inventory write ownership.
People/RBAC supplies identity and scope.

`InventoryPurchaseOrdersWorkspace` owns the Purchase Orders list, outlet scope, Draft editing, lifecycle dialogs, export and mutation read-back. Its focused read boundary uses the shared complete-read contract for scoped headers and identity-constrained lines/receipts/receipt items, with explicit incomplete/error states and scope-response guards. New-scope loading never exposes previous-scope orders; same-scope refresh may retain verified data. Historical duplicate orders remain separate readable records.

Stock Check hands off only submitted check identity to `InventoryStockCheckRestockSurface` at `/restaurant/inventory/purchase-orders/restock/:checkId`. That PO-owned workflow uses the canonical submitted-result reader, frozen shortage evidence, required supplier/item context and existing source reservation state. It owns suggestion selection and atomic supplier Draft creation through the existing command, preserving request identity/payload for unchanged retries. The entry retains Stock Check route access plus existing create/review eligibility; it does not merge PO commands into Stock Check. Both PO workflows reuse the identity-based detail/Receiving surface and publish canonical Inventory revalidation after successful mutations. InventoryControlPage retains route dispatch and shared Auth/UI/outlet/supplier context only.

Master Inventory is owned by `inventory/master/InventoryMasterPage` and its focused service. The route owns catalog filters, item/category/UOM forms, import/export, media sequencing, cost edits, and mutation read-back. Its atomic, exact-complete catalog read contains items, categories, UOMs, item-outlet links, item-outlet supplier links and scoped cost change summaries; a new Auth/outlet scope cannot expose the prior scope's rows, while a same-scope refresh retains the last verified catalog with an explicit failure state. Item writes preserve out-of-scope outlet links and surface partial link-save failures. Category deletion keeps its exact server count; UOM deletion uses the complete authoritative item-usage read and fails closed on incomplete/error reads. InventoryControlPage dispatches Master with Auth/UI/outlet context only. Shared item normalization preserves an explicit `archived` status when the active flag is false; the ordinary Master Archive action currently writes `inactive`, so this does not add a new lifecycle transition.

### Master Inventory Cost History

Master Inventory unit cost is global per item and expressed in that item's inventory UOM using up to four MYR decimal places. The Inventory-owned `inventory_authority.item_cost_revisions` history is append-only. `inventory_master_revise_cost` validates scoped Master view and edit access, current UOM, reason, request replay and expected previous revision. It serializes writes per item and updates the existing `inventory_items.cost` and confirmation metadata in the same transaction as the current-cost projection. `inventory_master_cost_history` exposes history within the Admin's Master Inventory item scope. Other consumers continue reading the canonical projection. Purchase Input does not write standard costs.

The migration records previously confirmed valid costs as baselines using the known recording timestamp and actor where available. Baselines carry no effective date, and unconfirmed defaults remain unconfigured. Configured zero is valid. New changes require a later effective date than the latest dated cost, up to today in Malaysia time. A dated revision can be corrected explicitly at the same effective date. The correction keeps the original entry and names both its predecessor in recording order and the revision it supersedes. Correcting an older date leaves the current cost intact. Cost corrections are scoped to the current UOM basis. Earlier revisions retain the original quantity and price basis. A UOM cutover appends an equivalent cost-basis revision when a cost is configured. This revision carries no price delta, is excluded from Cost Insights, and starts a separate comparable trend in Cost History. Item setup and catalog imports leave cost maintenance to the Cost History drawer. Submitted Audit snapshots and approved Closing Stock remain pinned to their original costs.

### Master Inventory Item UOM

The Master Inventory item unit is the single UOM for new stock and purchase activity. Edit Item gives access to Change UOM, UOM History and the separate Cost History. The Inventory-owned change command requires scoped access to all affected outlets. When quantity or cost evidence exists, Edit Item asks how many current units equal one new unit. An item with no dependent evidence can change units without a conversion. The revision records both units, any supplied conversion, a system-generated reason, the effective date in MYT, the actor and the server timestamp. The change takes effect on save. A retry or unchanged unit does not append history.

The cutover converts saved Par, active recipe lines with a matching basis, and configured standard cost atomically when the existing field precision can represent all equivalents exactly. UOM History retains the prior Par and recipe evidence. Finish or discard open stock counts, including audit correction drafts, and resolve open purchase orders and active recipe lines with missing or incompatible units. A scheduled draft whose recorded MYT business date has passed stays in history as Missed. It still requires a conversion for the item’s historical unit basis, and it no longer blocks the change as open work. Undated and future scheduled drafts remain blocked. Earlier Stock Checks, purchase orders, receipts, movements and inactive recipes retain their recorded quantities, units and available pinned costs. A historical record with missing unit or cost evidence displays the value as unavailable. Stock Evidence remains unverified against the new Par basis until a new count supplies comparable evidence. Submitted Audit evidence and approved Closing Stock remain immutable.

Legacy purchase-unit configurations and order pins stay in storage for compatibility. New POs use the item UOM. Older pinned lines keep their order and receiving unit, and the canonical receipt transaction continues posting inventory movements using their recorded factor.

Admin PO detail and Receiving are owned by `InventoryPurchaseOrderSurface`. Callers pass only PO identity, optional initial detail/receive/copy intent, and shared Auth/UI/outlet/supplier context. The surface owns scoped complete detail/receipt reads, stale-response protection, Receiving form/command, clipboard fallback and post-command read-back. PO projections and Receiving validation live in the PO service; the existing lifecycle RPC remains the sole receipt/stock authority. Receipt item reads are constrained to the returned receipt identities. Successful Receiving emits an `inventoryRevalidation` notification with PO/outlet identity; mounted Inventory readers revalidate using their existing complete-read owner. This is a notification boundary, not a cache, stock calculator or global data store. A committed receipt followed by failed read-back shows a read/retry state, never another submission of that receipt.

The business-facing PO No. is `inventory_purchase_orders.business_po_no`, assigned once by the database at creation and immutable thereafter. Existing three-digit Admin display numbers were frozen during the forward-only migration; new numbers start with a two-digit per-prefix/UTC-day suffix, expanding past 99 rather than wrapping. A private atomic counter and unique index protect concurrent creation. `po_no` remains a technical compatibility field, not a Crew display formatter. Admin and Crew read the same persisted number; Crew's opaque-session projection includes it in both list and detail.

Draft PO persistence and completed Stock Check suggestion conversion use trusted commands; the latter creates supplier drafts atomically and validates source, shortage line, supplier link and duplicate eligibility under a source lock. Submit, supplier confirmation, cancellation and completion use `inventory_transition_purchase_order` with server-derived state, time, scope, retry identity and audit evidence. An unconfirmed, unreceived Submitted PO may use the same trusted transition core to return to Draft for correction; the PO ID is retained, prior submission and return-to-Draft remain in audit history, and resubmission creates new submission evidence. Admin requires PO edit permission; Crew requires the existing outlet-scoped PO management capability. Supplier-confirmed or received POs cannot return to Draft. Receiving retains `inventory_receive_purchase_order` as the receipt and Purchase movement authority through the same private actor-explicit lifecycle core. Crew receives no direct table grants for these lifecycles.

Prospective Stock Check/supplier PO uniqueness is backed by the private `inventory_authority.purchase_order_source_reservations` key. Migration captures every existing non-cancelled PO ID without modifying historical orders, receipts, movements or request evidence, including legacy duplicate pairs. A transactional PO row trigger acquires the unique reservation for new inserts/key changes/reactivation; existing same-key lifecycle progress does not acquire another claim. Cancelling a PO removes only its own active membership; completed or other non-cancelled siblings keep the key occupied. Once all claims are cancelled an authorized replacement may reserve the key. Original captured membership remains retained privately. Clients cannot read, forge or release reservations. Existing source locks, request fingerprints, source-item validation, permissions and lifecycle audit remain independent requirements. Production release manifests where the earlier global source/supplier index was never applied substitute the forward reservation migration for that incompatible index; already-applied environment migrations are never rewritten.

Crew Inventory Gateway adds token-bound outlet Stock Check, Purchase Order and attention reads plus narrow Crew wrappers around those same private lifecycle cores. Reads never create checks, orders, receipts or movements. Fixed-outlet Crew is restricted to its Employee workplace outlet; Management must supply a currently Role-authorized outlet and hold the matching outlet Special Access grant. The four independent grants are Perform Stock Check, Create Audit Stock Check, Create / Manage Purchase Orders and Receive Purchase Orders. Crew may submit and supplier-confirm a PO, but cancellation and manual closure remain Admin-only. Crew receipt posting still uses the canonical Purchase receipt and Inventory movement transaction, with the employee actor recorded separately from Admin Auth.

Crew Purchase Order History is an outlet-scoped, token-bound projection of Completed, Fully Received, and Cancelled orders. Crew may select only the current Kuala Lumpur calendar month or the immediately previous month and filter by those terminal states. Newest-first results load in pages of 20. Active and Draft reads and all PO lifecycle commands remain with the existing Inventory PO authority. This Crew visibility window does not alter or delete older orders available in Admin.

Crew Stock Check History uses a token-bound, outlet-scoped month reader. History belongs to the Kuala Lumpur calendar month of the canonical check or scheduled date, regardless of when a check was submitted or skipped. Crew may select the current month or its immediately previous month, with All, Completed, Missed, and Skipped status filters. Results are newest first by check date and loaded in pages of 20. Terminal detail uses the same check-date visibility boundary while retaining the actual submission or skip timestamp as evidence. The gateway keeps current operational work separate from this history reader. Older check evidence remains in canonical tables and Admin workflows; the Crew month limit is a visibility rule, not retention.

The Crew mobile Operations surface consumes that gateway for Required/Audit/History counts, manual or Stock Check-sourced PO drafts, supplier confirmation, Copy Text and partial/full receiving. It never creates parallel Task, Stock Check or PO records. `crew_inventory_mobile_catalog` is a read-only, token-bound creation-choice projection for the outlet's active categories, items and suppliers; it does not grant item-master mutation or bypass any command validation. The Stock Check detail/history projection also exposes the current canonical Master Inventory image when one remains available, including for inactive items, without changing immutable count evidence. `crew_outlet_scope` exposes fixed-outlet inventory grants for action visibility, while every read and mutation still independently revalidates the opaque session, outlet and capability server-side. The PO text uses the same pure formatter as Admin.

Manual PO item pickers in Crew and Admin use the active item, active outlet configuration and explicit supplier link for the selected outlet. Changing suppliers confirms removal of incompatible lines and keeps compatible quantities and units. The shared draft save command validates current eligibility for new lines and supplier changes; an existing manual draft can retain its saved items with the same supplier if links have since changed. Stock Check shortage validation and receipt posting remain separate.


Scheduled Stock Check occurrences use the outlet's server-side Kuala Lumpur business date and configured group schedule: Due, In Progress (persisted draft), Completed (submitted), or Skipped; an unresolved occurrence becomes Missed after its business date. Required and Home expose only current Due/In Progress occurrences. Historical drafts are read as Missed and cannot be saved or submitted after their date; missed schedule runs without a persisted check are read-derived for the recent seven business dates in History, not fabricated count records. Legacy duplicate rows are retained as evidence but projected as one occurrence, preferring Completed then Skipped. Crew may skip only a currently Due occurrence through an outlet/capability-checked, idempotent command that records actor, business date, server time, and optional controlled reason. Skipped evidence is terminal and immutable; it neither counts stock nor creates a purchase suggestion or movement. History includes completed scheduled checks, Skipped, Missed, and completed Audit checks whose check dates fall inside the selected month. Audit remains count/control evidence only and is never a PO source. Existing completed counts and product-image presentation remain unchanged.

After a completed scheduled Stock Check, Crew's completion result uses the existing token-bound PO suggestion projection to offer a direct review of eligible Par-level gaps. That projection also supplies counted quantity, Par quantity and source-linked PO identifiers for display and re-entry; it is not a second suggestion calculator. Crew reviews supplier grouping, item inclusion and requested quantities before invoking the existing atomic source-check-to-draft command. The command retains all source, supplier, duplicate and race checks; no PO is submitted automatically. Audit checks remain ineligible, and a source already represented by a PO resolves to that canonical order rather than creating another.

## Compatibility And Deferred Scope

Inventory Movements and Stock Check Admin lists select one accessible outlet at a time; neither combines records from all accessible outlets. Movement transfer-reference detail may load the linked pair by identity within accessible outlets on demand. This is a list-scope presentation/read constraint, not a change to transfer or Stock Check lifecycle authority.

Submitted Scheduled and Audit results share `InventoryStockCheckResultSurface`, opened through the canonical nested `/restaurant/inventory/stock-check/results/:checkId` route. This identity-only entry bypasses the legacy Inventory bootstrap and owns complete header/item reads, required catalog/category/actor labels, permission/outlet checks, stale-response guards, result filters and photo viewing. `inventoryStockCheckResultService` is the shared submitted-evidence reader, including for the existing restock handoff; Stock Check normalization lives in `inventoryStockCheckReadModel`. List and Detail resolve the creator from the recorded employee ID, using the stored Auth ID through the employee Auth link when no creator employee ID was recorded. Submission is attributed separately through the recorded submitter employee ID. An unresolved creator is never replaced with the submitter. Catalog joins never replace submitted quantities, Par, variance or pinned costs. The existing Audit valuation projection is unchanged. Draft/counting/submission belong to `InventoryStockCheckPage` and its focused execution reader; PO/restock commands remain independent. The execution owner reads outlet-scoped groups, item/Par context, check headers and active Draft rows through exact-complete reads. Historical Audit lists use the canonical scoped `inventory_stock_check_row_summaries` projection for item, shortage, excess, and skipped counts. Shortage and excess compare each row’s stored Actual and Par in its original unit. Skipped, pending, unavailable, and missing or invalid quantities are excluded from both counts. An explicit zero is comparable. Draft rows use the same rule locally. The list displays Closing Month only when it is recorded on the audit. Historical cards do not transfer submitted rows. Opening a submitted Result still reads its complete immutable evidence through the independent Result owner. Scope changes cannot expose the prior outlet's data. Scheduled and Audit drafts use the existing lifecycle commands and hand off submitted identity to Result or Restock.

Recipes and Product Mapping are owned by `inventory/recipes/InventoryRecipesPage`: outlet selection, filters, workspace state, recipe/ingredient/clone/photo forms, menu-category management, export and existing mutation orchestration. Its atomic verified read contains outlet recipes/ingredient lines, inventory catalog, outlet links, categories and menu categories only. Cross-outlet clone sources load on demand across accessible outlets; Product Analytics and mappings load only when Product Mapping opens. Exact-complete Product Analytics reads remain in its canonical service, and errors/incomplete reads never appear as genuine empty mapping results. Scope changes invalidate stale responses. Recipe normalization, cost display and shared mapping projection live in `inventoryRecipeReadModel`. Writes retain existing recipe RPC/category/mapping/media authorities and emit notification-only Inventory revalidation. InventoryControlPage dispatches Recipes with Auth/UI/outlet context only.

Recipe Intelligence is owned by `inventory/recipeIntelligence/InventoryRecipeIntelligencePage`: outlet/forecast-period/report-month/year and trend selections, consumption drill-down, charts, read/retry and revalidation. Its atomic complete read uses canonical recipe sources, only the ingredients referenced by those recipes (including inactive costing context), category/menu context, outlet mappings and Product Analytics reports/items covering the forecast, selected month and trend year. It does not mount the Inventory bootstrap. The route consumes Phase 5's recipe/mapping projection; its pure analytics owner preserves the established profit, consumption, forecast and trend formulas. Pending/ignored products remain excluded from mapped analytics. Failed/incomplete reads hide charts/results rather than masquerading as empty analytics; outlet/period/identity changes reject stale responses. Inventory revalidation is notification-only. No second mapping command surface exists, and the parent supplies only Auth/outlet context to this read-only analytics route.

Movements / Transfers is owned by `inventory/movements/InventoryMovementsPage`: accessible-outlet movement reads, filters/pagination, header, manual movement and paired-transfer forms/commands, reference detail entry and refresh. Its complete read bundle contains movements, item context and actor display context only; shared shell outlet/Auth/UI inputs remain external. Scope changes and unmount invalidate stale reads, and failed/incomplete reads never become empty or partial authoritative tables. PO references resolve by identity (legacy business references are looked up on demand) into the canonical PO surface; Wastage references enter the Wastage-owned identity detail. No PO/receipt/Waste bootstrap is required. Mutations retain the existing lifecycle service/RPCs and publish the notification-only Inventory revalidation boundary; committed intent closes before read-back. Parent dashboard/other workflows may still read movements for their own projections, not control this route.

Par Levels is owned by `inventory/parLevels/InventoryParLevelsPage`, including accessible outlet selection, outlet/matrix presentation, filters, grid navigation, autosave intent/response sequencing, supplier assignment, export and photo preview. Its four-collection complete read loads items, categories, outlet configurations and configuration-supplier links together; it does not mount Stock Check, PO, Movement, Waste or Recipe bootstrap reads. Failed/incomplete reads block the data surface and scope changes invalidate stale reads and save responses. Successful autosaves apply the returned canonical configuration without a broad refetch, preserving the existing persistence behavior. Shared item/outlet normalization now lives in `inventoryItemModel`; existing Inventory consumers use that same projection rather than duplicating it in the extracted route. No stock or transaction authority changes accompany this extraction.

Wastage is owned by `inventory/waste/InventoryWastePage`: required accessible outlet, filters, header, form/evidence state, existing lifecycle service intent, photo viewer and coherent post-mutation refresh. Loading, incomplete/error reads and stale scope responses cannot become authoritative empty/partial results. Stock Check Groups is owned by `inventory/groups/InventoryGroupsPage`, including required accessible outlet selection, filters, scope details, header actions, GroupModal, existing group/category-link commands and mutation refresh. InventoryControlPage only dispatches this route and supplies Auth/UI and canonical outlet inputs; Groups does not mount the legacy Inventory bootstrap. Its five-table read plan (groups, group-category links, items, categories, item-outlet links) uses exact complete reads, joins atomically, rejects partial/error results, and guards stale responses. Execution/history and other Inventory routes retain their existing owners and authorities.

Full Inventory reads page each canonical collection with exact counts and stable ID tie-breaking through `inventoryCompleteRead`. Read failures, changing counts, overlapping pages and truncation are explicit error/incomplete states, never authoritative empty collections. Only a verified complete read replaces the full Inventory projection. Initial loading and failed refresh block the full data surface; successful-snapshot revalidation is explicitly marked. The focused PO reader and all stock/PO/receiving write authorities remain unchanged.

Inventory Control and Asset Tracking pages are surfaces within this domain, not separate documentation domains.
Do not merge Factory warehouse state into restaurant inventory solely because both represent stock.
Advanced costing, predictive ordering, or external warehouse integration remains deferred unless introduced by current contracts.

## Restaurant Agent Operations

The shared Gateway adds explicit, outlet-scoped capabilities without granting existing Agents access. Asset reads include canonical categories, condition templates, inspection/maintenance headers and item evidence. Supported actions are Asset Create/Update, Inspection Create/Update/Complete and Maintenance Create/Update/Complete. Inspection completion requires an explicit observation date, observed count/condition and applicable template photo/remark evidence. Maintenance completion requires actual action taken and completion date. These are genuine evidence inputs, not attestations inferred from an instruction.

Inventory capabilities cover Master Inventory, Par Levels, Stock Check, Purchase Orders, Movements, Wastage and Recipes & Usage. Supported commands are scheduled Stock Check draft Create/Update/Submit; PO Create/Update/Submit, supplier Confirm, Return to Draft, Cancel, Complete and Receive; manual Adjustment creation; Waste creation; Recipe Create/Update. Receiving and Waste post only their existing canonical movements. Manual Adjustment cannot forge Purchase/Waste references. Item/ingredient references must belong to the selected outlet. Submitted counts and received PO evidence retain existing immutability.

Master Inventory/Par writes, Audit-mode Stock Check commands, transfers and media upload are not exposed by this adapter. Recipe/usage reads expose saved recipes and ingredient mappings, not a parallel forecast or live-stock calculation. These limitations do not remove Human/Crew operations. Gateway permissions, scope, retries and audits follow `../architecture/trusted-authorities.md`.
