# Crew Operations

## Purpose And Scope

This domain owns operational tasks and Daily Operations, task schedule/assignment/completion, Cash Checkout, Floating Cash, Deposit Ledger, and cash Handover.
It covers the daily execution layer used by outlet Crew and supervising Admins.

## Canonical Ownership

Current task, operations-template, daily-instance, cash-checkout, collection/handover, deposit-ledger, RPC, RLS, and contract tests are authoritative.
Crew Workforce owns employee access, roster, attendance, and leave.
Crew Localization owns translated content state and fallback behavior.

## Core Entities

- Task and Daily Operations templates, schedules, assignments, instances, and completion evidence
- Outlet/date/position and roster-derived execution context
- Cash settings, effective Floating Cash, immutable float adjustments, and tolerance rules
- Daily Cash Checkouts, denomination evidence, variances, reviews, and retained/deposit amounts
- Cash collections or handovers, receiver confirmation, deposit ledger entries, corrections, and receipt evidence

## Lifecycle And Business Rules

Published or active task definitions create scheduled operational work according to current assignment rules.
Crew receives only work applicable to its validated session, outlet/date/position context, and assignment. A scheduled run has one canonical operational occurrence identified by Task series, outlet and business date, independent of template revision. Revision activation and run materialization serialize by series; a partial unique index enforces one operational occurrence. An unstarted run adopts the latest effective revision. The first response permanently pins the run snapshot and responsibility, including after Reset; later revisions apply to future runs. Completed executions remain frozen. Superseded occurrences retain their original snapshots and responses for Admin audit but are unavailable to Crew reads, writes and notification actions. Admin Execution History and progress counts consume the same canonical operational occurrence flag, so each scheduled run appears once at its actual frozen revision. Admin also reuses the shared assigned-Crew execution-status authority to resolve older started runs whose occurrence status remained Not Started. Versions retains all template revisions and audit occurrence counts; superseded rows are not additional operational executions.

Incomplete responses are mutable working state. The token-bound Reset authority restarts the same occurrence, clears the current actor's unfinished responses for individual completion rules, or the shared unfinished response set for `one_for_team`, and records a lightweight reset audit. Reset does not create another execution/version, unpin the run, or alter completed evidence. Response writes, resets and completion serialize on the occurrence row. A response guard rejects mutation of completed, reviewing or non-operational evidence. Duplicate-run reconciliation records the canonical/superseded relationship without copying or merging incomplete responses.

Platform Notification V1 consumes canonical Task occurrences, never recurring templates. A scheduler-owned, Malaysia-time projection creates one deterministic actionable notification per occurrence/assignee, important for one-off work and normal for recurring work. It separately creates exactly-once due-soon and overdue reminders only while the assignee remains incomplete; completion suppresses future reminders. A material assignment, availability, due-time, or cancellation change to an actionable occurrence may produce an important change notice. Notification delivery/read never starts, saves, resets, or completes a Task.
Crew execution status resolves valid responses from assigned Crew: a started response set cannot project Not Started, including older stale assignee states. Shared `one_for_team` writes mark the assigned team In Progress together; other completion rules retain actor scope. Past unfinished runs remain visible in bounded History. One shared Crew presentation resolver derives Upcoming before availability with zero responses, Start Now during the window with zero responses, In Progress with responses, and Overdue after the due time regardless of progress. Completed, exception and review semantics remain canonical. Home, Active Tasks, History, Detail and status filters share this resolver and retain progress counts; these labels never authorize writes or change persisted lifecycle state. This projection does not rewrite response or completion evidence. Completion and review transitions are server-controlled and preserve required evidence.
Crew All Tasks History is a token-bound, fixed 30-calendar-day execution projection; it cannot widen the Crew query window and does not alter Admin's full task audit history. Crew Task Detail projects responsibility from the frozen instance assignment. Completed by lists distinct assigned Crew who supplied valid responses to that execution, excluding untouched assignees; individual execution rules retain their person-specific scope. The final responder/completion actor and time remain separate in completion audit authority. Completed items show one compact result while retaining recorded comments and evidence. Home places completed Tasks after actionable Tasks without changing their statuses or the existing actionable priority/due ordering. For `one_for_team`, the assigned team shares the actual item response results and progress in Detail, Home, and Task lists; response rows continue to identify the Crew member who submitted each result. Required-item completeness and the final occurrence transition use valid responses from frozen assignees under an occurrence lock; the last required response supplies the completion actor, while each item retains its own actor. A restricted, audited reconciliation may finish an older stranded occurrence only when its existing assigned-Crew evidence already satisfies every required item; it never rewrites response rows. Other completion rules retain per-Crew item projections.

Cash Checkout is an outlet/date lifecycle with controlled draft, submission, review, completion, and canonical calculation states. Manager Return uses the existing review authority to send the same submitted checkout back to its submitting employee, with a required reason. Returned working state is `reconciled`/`draft` with rejected review and projects as Returned / Action Required, separately from submitted pending review (Needs Review). Crew sees the reason throughout correction and can resume a returned prior-day run by its checkout ID; employee ownership, outlet authorization and current checkout eligibility remain enforced. Correction preserves the recorded opening/float basis and the existing cash calculations. Resubmission always requires Manager approval after a Return, even if the corrected variance is balanced; it is not cancellation or a new checkout. Submitted financial fields are read-only until Return. An append-only private review-event journal retains each submitted/resubmitted financial snapshot, return reason, real actor and server time, then final approval/completion; the shared checkout projection exposes compact Review History to Admin. Existing recorded submission/review timestamps remain visible without manufacturing historical decisions. Returns/resubmissions post no Deposit entry: only final completion posts the existing single obligation. Completed checkout/ledger evidence remains immutable. Return, editing and review serialize on outlet/checkout locks and reject stale lifecycle actions.
The server calculates opening expectation, counted totals, closing variance, retained float, carry-forward, and amount for deposit. POS Closing Cash already includes Floating Cash, so closing variance is physical count minus POS Closing Cash; Floating Cash is not added or subtracted from that comparison. Opening float and previous carry are reference values, while current float is retained when allocating counted cash for deposit and handover. A mutable checkout whose old client-populated opening default is stale after a float adjustment can continue without treating that default as an observed opening variance. Recorded opening exceptions and completed checkout evidence remain intact.
Floating Cash changes use the authorized cash authority and create immutable adjustment evidence. Admin Floating Cash amount controls and their dedicated read-only History sit outside general Cash Checkout Settings; saving variance, eligibility, handover, or review rules does not change the stored float amount or adjustment history. The Admin read model reports the current effective amount from dated adjustments, including when a later change is already recorded.
Cash Checkout settings are outlet-scoped. Eligible checkout positions are configured by canonical Job Position IDs; the server retains derived position names only as compatibility input for the employee master, which currently stores position names. The effective Floating Cash value comes from the latest applicable immutable adjustment, while each checkout snapshots its Floating Cash and variance tolerance so later settings changes do not rewrite history.
Management Checkout eligibility is a separate outlet setting, disabled by default: active Management with active Crew Access must have current canonical Role authorization for the selected outlet and that outlet's “Allow authorized Management to perform Cash Checkout” toggle enabled. Crew retains fixed outlet employment and configured Checkout Position eligibility; Management is never added to the position catalog. The shared cash eligibility predicate governs read projections, Me navigation and every checkout save. The Management outlet adapter delegates Count → Allocate → Confirm to the existing cash calculation/save authority and records the real employee actor and ledger evidence. Toggle changes are Admin-permission/outlet checked and audited. They grant neither Initiate Cash Handover Special Access nor configured Receiver eligibility, and do not broaden Task execution authority. Disabled or revoked outlet eligibility is revalidated on subsequent cash commands.
Variance tolerance and the review-over-tolerance switch control server-calculated review state. Internal receiver confirmation controls both Crew- and Admin-created handovers; when disabled, an internal handover completes without a pending acknowledgement while still posting only one ledger debit. Closing deadline is currently stored and exposed as operational reference but does not gate or transition Cash Checkout; future enforcement requires an explicit lifecycle contract.
Crew Checkout History is a bounded, outlet-scoped read projection of completed Cash Checkout snapshots from the requested business date's preceding 30 calendar days; it never derives history from Deposit Ledger entries.

The Deposit Ledger is append-only financial evidence derived from completed obligations, submitted collections, deposits, and explicit corrections. A submitted collection immediately posts its single debit; recipient confirmation is acknowledgement evidence and never posts a second debit.
Internal handover remains pending confirmation until the intended receiver confirms through a valid Crew session. Cash Handover initiation requires the active, outlet-scoped Crew Access capability, independently of Admin roles and receiver eligibility. New handovers use one canonical `Cash handover` purpose because all follow the same collection, confirmation, ledger, and accounting lifecycle; historic purpose text remains preserved as submitted evidence. New handovers may be addressed only to an active Crew account explicitly configured by an Admin as a Cash Handover Receiver: either Crew whose canonical Workplace is the outlet, or Management whose current Role outlet authorization includes that outlet. Receiver selection never grants Initiate Cash Handover Special Access. Receiver-only Management can view and confirm its assigned receipts for an authorized selected outlet without Cash Checkout or deposit-ledger authority; receiver configuration is versioned and audited, while removing a receiver never rewrites or strands existing assignments.
Corrections cannot silently rewrite completed checkout or ledger history. Completed allocation corrections append structured original/before/after Carry Forward and For Deposit evidence to the existing correction journal, retaining the real Admin actor, server time, reason and predecessor. The trusted allocation command preserves Counted Cash, Floating Cash, POS Expected, Variance and the recorded retained-cash envelope. It serializes on the outlet and checkout, requires the expected prior allocation correction and a unique request ID, rejects no-ops/stale editors/reused requests with changed intent, and posts exactly one linked net Deposit Ledger adjustment atomically. Admin and Crew detail/history plus next-day carry use one private effective-allocation resolver; the original completed checkout and original ledger obligation remain immutable. Existing generic ledger adjustments/reversals remain separate; an allocation correction fails closed after such evidence, and a subsequent generic reversal uses the corrected deposit amount. An already finalized later checkout is never recalculated. Corrections that would make the Deposit balance negative require reconciliation of the existing Handover evidence first.

Crew Admin Tasks, Manager Review, Daily Cash Checkout, and Cash Deposit Ledger use server-paged read projections (20/50/100 rows). Scope, date, search, and lifecycle filters apply before pagination; the Deposit Ledger's page is independent from its canonical append-only balance summary. Crew Cash projections resolve actor display through the canonical `employees` identity: Crew uses its employee name and Admin uses its People/Admin employee name. If no human display identity exists, the projection returns the safe `Admin` label; it never projects a raw auth email. Immutable employee/auth actor IDs remain stored audit evidence and are never rewritten for presentation.
The Tasks definition page projects its original series creation timestamp and linked employee display name through the authorized paged read; missing human identity displays as unavailable, never a raw Auth ID or email. Its Time Window reads persisted start/due times independently from schedule recurrence and date.
Admin Tasks opens with Status All and a bounded Today range. Clearing its date picker or all filters restores that same effective range; changing filters resets server paging to page one. The bounded paged RPC contract does not accept an unbounded date range.

Management Task Detail uses the same internal evidence projection as assigned-Crew detail after validating the live opaque session and selected Role-authorized outlet. Management can inspect shared team evidence and each assignee’s separate execution for individual completion rules, including actual contributors and response actors. This read authority is non-materializing, excludes non-operational occurrences and grants no execution, completion or Reset rights. Task translations use the same authorized outlet boundary.

## Permissions, Snapshots, And Audit

Admin task and cash actions require the relevant Crew Operations permission plus outlet scope.
Crew mutations are token-bound to the current employee and eligible work.
Published task/content versions, completion evidence, cash calculations, float adjustments, handover confirmations, and ledger entries retain immutable or append-only history.

## Admin And Crew Workflows

Admins create and publish operational templates, monitor daily execution, review exceptions, configure outlet cash rules, review Cash Checkouts, coordinate collections, and inspect the Deposit Ledger.
Crew view assigned daily work, complete tasks with required evidence, perform eligible Cash Checkout steps, and confirm assigned handovers.
Task Builder uses shared branded date/time fields. The service maps template `available_from` / `available_until` time-of-day values to builder `start_time` / `due_time` fields for lossless Draft editing; server schedule constraints remain authoritative. Crew Home, Task rows and detail use one shared priority indicator: Normal is quiet, Important secondary, and Critical explicit. Priority presentation does not change task eligibility or execution.
Crew Home exposes outlet-scoped Stock Check and Purchase Orders action lists when the selected outlet has corresponding Special Access. These lists show the complete actionable rows returned by the bounded token-bound Inventory projections, not duplicate Daily Tasks or completed history. Stock Checks prioritize overdue scheduled drafts, due checks, then other resumable drafts; POs show manageable drafts/submitted orders and receivable confirmed/partial orders. The PO read projection derives category names from canonical Inventory items for compact Home context without changing PO lifecycle authority. Fixed-outlet Crew use their workplace outlet; Management must select a Role-authorized outlet and hold each outlet-specific Special Access independently. Home clears prior outlet rows while reloading, and Inventory screens remount on outlet changes so prior outlet state cannot remain actionable.

Crew `From Stock Check` purchasing exposes only remaining below-Par suggestions from a scheduled check submitted within the latest seven days. The token-bound read and both Crew source-order command paths enforce this window against the server timestamp; existing drafts and idempotent retries remain governed by the canonical PO lifecycle. The Crew PO detail read projects Master Inventory imagery, item codes, category context and lifecycle dates without creating Crew-specific item authority. `Receive All Remaining` only fills local quantity inputs; the canonical receipt/inventory movement command still runs solely after explicit `Record Receipt`.

## Integrations

Crew Workforce provides secure sessions and roster-derived context.
Crew Localization supplies translated task snapshots and fallback behavior.
Crew Learning may supply SOP references or required knowledge but does not own task completion.
Crew Performance may consume controlled completion and cash evidence without mutating operations history.
Restaurant Finance may consume summarized cash evidence without owning the Crew cash lifecycle.

## Compatibility And Deferred Scope

Legacy task or operation-template route names resolve to this domain's canonical owners.
Tasks and Cash Checkout remain grouped because both are outlet daily execution lifecycles; their entities and permissions remain distinct.
Bank API integration, automated deposit matching, and payroll deductions are deferred unless explicitly introduced.

Cash Checkout cross-day resolution preserves the original checkout ID and business date. `reconciled` is the mutable Allocate step; final evidence is `completed`. Earlier unresolved Draft, Allocate, Returned and submitted review states surface as Previous Day / Action Required independently of History date filters. The submitting eligible employee may continue an earlier run through the same workflow; submitted evidence requires Manager Return before editing. Authorized Manager review or the eligible submitting employee may cancel a non-terminal checkout with a reason. Cancellation preserves all recorded cash fields and appends actor/time/reason/snapshot evidence; effective deposit and carry are zero, no ledger is posted, and the cancelled run is immutable and retained in History. A cancelled outlet/date is not reused for another checkout. Completed runs retain audited Correction as their sole correction path.

The private cash-chain resolver identifies every earlier unresolved run and returns no verified previous-carry amount until those runs are completed or cancelled. Count, save and submission may proceed with an explicitly provisional basis; Crew completion and Manager approval cannot finalize while predecessors remain unresolved. Once a run starts, its recorded opening/float basis is preserved. A later resolution or audited allocation correction that changes its carry basis appends Review Required evidence without rewriting financial fields; the later run requires Manager review. Review records the saved evidence and current resolved chain basis. Outlet serialization covers continuation, cancellation, review, completion and allocation correction. Finalized later evidence is never recalculated.

Submitted Cash Checkouts await a Manager decision even when legacy variance exception flags say `not_required`. Admin row status, Needs Review count, and review actions use the canonical Submitted lifecycle; Returned stays distinct and requires Crew correction.
