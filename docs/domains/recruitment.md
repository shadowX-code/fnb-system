# Recruitment and AI Interview

## Ownership

People owns Recruitment before employment. `recruitment_applicants` identifies a person and `recruitment_applications` connects that person to an opening. Neither is an Employee, Auth user, or Crew identity. Position, workplace, Legal Entity, and eventual Employee creation remain with their existing People and Restaurant masters. An opening targets exactly one canonical workplace and one active Legal Entity in V1. Restaurant workplaces resolve to an Outlet; Factory and Management are the established non-outlet values.

The `recruitment` module is one Admin workspace at `/people/recruitment`. `recruitment.view` reads scoped openings, applications and interview state; `recruitment.manage` also saves openings, registers applications, and issues/revokes invitations. Restaurant outlet scope is checked for outlet-targeted openings. Phase 1 introduces no manager hiring decision or Employee conversion.

## Opening and interview configuration

An opening is Draft, Open, or Closed. Closed openings cannot reopen in Phase 1. An opening references an existing Job Position and Legal Entity. Published job-facing values are snapshotted on each application. Position, workplace and legal employer cannot change after an application exists.

Every opening save creates a versioned interview configuration. It contains required evidence topics, scenario briefs, EN/BM/Chinese language guidance, target and maximum duration, candidate instructions, and conversational AI instructions. Required topics are evidence targets, not a universal question script. An invitation creates one durable interview attempt pinned to the opening's current configuration version. A later opening edit does not alter an issued attempt.

## Invitation and candidate preparation

The server creates a random 256-bit invitation token and stores only its SHA-256 hash. The public URL is `/i/{token}` on `interview.feedx.my`. Issuing a new invitation revokes earlier invitations for that application. Expiry, revocation, and Open opening status are checked on every public operation. Anonymous callers receive only a minimal job and profile projection; direct table grants remain revoked and all Recruitment tables have RLS enabled.

The candidate confirms a minimal name/contact profile, accepts versioned consent covering AI, camera/microphone recording and recruitment review, and checks devices before the attempt becomes Ready. Approved product copy `feedx-interview-v1-approved` uses one explicit checkbox covering those three existing purposes. Consent is a pinned copy snapshot with timestamp and application/attempt references. New acceptance must match the current copy; an identical retry preserves the original record. The latest approved version is selected for unconsented attempts, while accepted attempts retain their original version/snapshot, including historical `phase1-provisional-v1` evidence. No retention/deletion terms or Privacy Notice destination are inferred. The browser device check is a readiness declaration, not server proof of media quality. AI voice and recording begin only after candidate preparation and an explicit Start interview action. Hiring decisions remain outside Phase 2.

The public interface mounts separately from Admin and never creates candidate Auth or Crew access. The browser preview and microphone meter use a local media stream and release tracks on unmount. Device loss removes the local Ready check. The persisted Ready milestone indicates a successful check at that time; Phase 2 must require another check at interview start.

## Phase 2 interview authority

`recruitment_interview_attempts` owns Ready → Starting → Interviewing → Finalizing → Completed, with Interrupted, Partial and Failed outcomes. The server allocates a 45-second renewable single-client lease, provider generation and maximum end time. A refresh keeps a tab-bound client identifier in session storage; a Web Lock prevents a duplicate tab from opening the same attempt. The server lease still denies other clients. Refresh and foreground recovery require an explicit Resume action, fresh camera/microphone acquisition and a fresh recording unit/provider session. Configuration, transcript, topic/scenario progress and unresolved items remain pinned to the same attempt. An explicit interruption pins a server pause timestamp; resume restores the remaining active-time budget, bounded by invitation expiry. An expired lease conservatively uses the last acknowledged heartbeat as the interruption boundary. A resume always records a gap; it never implies uninterrupted capture. Every sensitive operation revalidates the invitation, opening and lease. Target duration guides the conversation; maximum duration is a server deadline. Finalization accepts completion through supported coverage, the deadline, or an explicitly partial candidate stop.

The Recruitment-owned `recruitment-realtime` Edge Function uses server-held OpenAI credentials to mint 60-second browser authorization. Browser WebRTC uses semantic turn detection with low eagerness and server input-noise reduction. Automatic response creation and interruption are disabled: one Recruitment response controller creates at most one response per committed semantic candidate item and owns cancellation/clearing on barge-in. Provider response IDs, generation completion and output-buffer playback completion fence tool continuations. Late tool results cannot take a newer candidate turn. A single in-flight reconnect and closed-session checks fence stale credentials, channel events and remote audio. OpenAI `gpt-realtime-1.5` supplies a non-reasoning conversational stream; the prior reasoning model could emit an audible commentary/preamble followed by a second message in the same response. Recording uploads recover independently and do not hold conversation resume until every prior file uploads. Opening-specific guidance supports EN, BM, Chinese and Malaysian code-switching. A reconnect creates a new provider session from server-approved recent durable finalized turns, covered-topic candidate statements, opening context, remaining active time and topic/scenario progress. Truncated AI text is omitted from continuation context; prior questions and utterances must not be replayed. It does not stop camera recording or import Guest AI device/session business contracts.

Recruitment presentation lives in `recruitment-realtime/voice.ts`: canonical profile `feedx-malaysian-interviewer-v1.1` retains the existing OpenAI `marin` voice and requests warm professional F&B conversation, subtle Malaysian English intonation, calm pacing, brief varied acknowledgements and one concise question at a time. It avoids stereotyped particles/exaggeration and treats candidate accent/code-switching neutrally. Presentation does not own opening evidence targets or completion permission. The interviewer briefly identifies itself as AI, follows useful missing details, tolerates pauses, and thanks/closes only after server permission. Prompted accent and naturalness are human acceptance targets, not automated guarantees.

Finalized transcript turns are append-only, idempotent by provider generation/item/speaker, ordered by provider conversation-item creation rather than asynchronous transcription arrival. Browser IndexedDB queues retries across reloads. Timing is approximate relative to the attempt start. Truncated AI speech and missing transcription are append-only annotations. Transcript source is explicitly `provider_event_relay`: browser relayed provider text is not independently attested provider evidence. AI transcript publication waits for provider output-buffer playback completion; interrupted/uncertain text is retained only with a truncation annotation and is excluded from resume context. Managers must compare it with recordings: output-buffer completion and browser playback observations do not independently attest what a candidate heard. No missing speech is reconstructed. Bounded browser-relayed diagnostics in `recruitment_realtime_traces` retain response/item IDs, VAD/EOS, response/cancellation ownership, provider/playback lifecycle and approximate elapsed timing. They contain no credentials, transcripts, prompts or audio. The token/lease validated batch RPC is idempotent; the table and single-record helper have no direct candidate/Admin grants. These diagnostics are operational observations, not hiring signals or provider-attested evidence. A provider disconnect conservatively makes the interview partial even when its recording remains complete.

The `recruitment-evidence` Edge Function assesses only topic/scenario coverage using finalized transcript text. It persists supported candidate-turn citations for required topics and ordered AI-question/candidate-answer citations for scenario asked/answered states. A volunteered answer before the AI presents the hypothetical cannot complete the scenario. Transcript text is untrusted input. The realtime AI requests permission to conclude; server coverage rules decide whether closure is allowed. These are collection progress indicators, not candidate suitability scores or Phase 3 summaries.

## Recording and upload evidence

One fresh `MediaRecorder` captures each uninterrupted foreground recording unit. Camera video and Web Audio mixed candidate/interviewer audio form one MP4 H.264/AAC container. Recording starts before AI authorization. Its five-second output blobs are transport bytes only: they are never treated as independently playable files. Delayed recorder events are split into transport chunks of at most 6 MiB without altering byte order. Each stopped unit concatenates those bytes locally to check nonzero video metadata, and uploads through immutable, individually acknowledged private transport chunks. The Edge Function streams the acknowledged bytes in manifest order into one finalized Storage file without loading the entire interview into server memory. Upload recovery reconciles existing private object size receipts before requesting another upload URL, including a lost acknowledgement. It retries missing chunks and file assembly; it never requires replaying acknowledged chunks. The final server verifier checks received byte count and complete MP4 box structure, audio/video tracks and nonzero dimensions using ranges; it does not perform a full codec decode.

IndexedDB preserves pending unit bytes. Private raw transport chunks have immutable path/size receipts and server acknowledgements; acknowledged chunks remain even if a final playable unit cannot be recovered. The `recruitment-evidence` private Storage bucket has no anonymous or authenticated direct access policies. Server-authorized signed upload paths derive from the validated attempt/unit; final files cannot overwrite existing evidence. Units are limited to 128 MiB, with a browser pause at approximately 100 MiB to allow a fresh capture. Up to 30 units are allowed per attempt.

Recording and realtime transport have separate failure boundaries. Network/upload errors queue bytes and retry while capture continues. Backgrounding, screen lock, reload, device loss or recorder failure ends the current unit best effort, records an explicit gap, and requires fresh camera/microphone access for the next unit. The same attempt and coverage continue. A unit lost with browser storage is marked interrupted; raw server receipts are retained. Unclosed surviving bytes can be retried but never imply continuous capture. Mobile browsers cannot guarantee a valid trailer or uninterrupted background recording.

Only server-verified finalized files receive manager playback links. Complete recording requires verified units, no explicit gaps or uncertain unit endings, and bounded coverage of the attempt timeline. Gaps or invalid/interrupted units remain partial; no verified playable unit is failed. Pending upload stays Finalizing. Missing candidate transcript, known transcription failure, early stop or provider disconnect makes the overall attempt Partial. `recruitment_admin_evidence` enforces `recruitment.view` and canonical opening outlet scope; the Edge Function returns five-minute private playback URLs only after that check. Managers see recording units, gaps, ordered transcript, coverage and unresolved items. Phase 2 creates no hiring decision, candidate summary, score or Employee conversion.

## Verified mobile boundary

Physical evidence supplied for iPhone Safari 18.7.5 / iOS 18.7 reproduced a valid first ~5-second MP4 unit and a second unit with 0×0 video metadata twice. iPhone Chrome 154 / iOS and Android Chrome 154 loaded both sequential MP4 units at 480×640. This establishes that independently stopped units also require integrity checks; it does not establish reliable repeated Safari captures. The implementation preserves the first valid unit and reports subsequent invalid or interrupted evidence honestly. No seamless background continuity is promised. Full-duration recording, mixed interviewer audio, resumable upload and recovery on those physical devices still require end-to-end validation; see [mobile evidence and limitations](../../qa/recruitment/mobileMediaValidation.md).

## Phase 3 reports and manager review

A finalized Completed, Partial or Failed attempt can enqueue a Recruitment-owned report in the finalization transaction. `recruitment-report` generates it after capture finalization; managers can continue a queued/expired generation or explicitly request a new version. Existing finalized attempts are prepared on manager request, without a backfill. No candidate transcript produces an explicit Unusable report, preserving available recording and human follow-up rather than assessing or rejecting the candidate.

`recruitment_reports` pins configuration, ordered transcript, coverage, unit integrity, annotations and gaps in a source snapshot and SHA-256 hash. Each version retains its model, prompt version, provider response identifier, actual provider model and generation result. The source is immutable from enqueue; Ready, Unusable and Failed results are immutable. A renewable generation lease prevents duplicate workers from publishing. An identical preparation request is retry-safe. Automatic preparation returns an existing report; a new version requires an explicit authorized manager action. Review acknowledgements and decisions retain the particular report version. Reproducibility means retained inputs/provenance, not guaranteed identical output from a nondeterministic provider.

Prompt v2 requires a short factual snapshot and an evidenced language overview; fixed evidence-health follow-ups disclose gaps and transcript failures independently of model omission. Original v1 reports/prompt remain retained. Reports include candidate-stated facts, AI interpretation, required-topic Covered/Partial/Unresolved findings, scenario findings and unresolved manager follow-ups. Material findings require same-attempt candidate transcript citations; absent-information follow-up items can have no citation. The trusted function sends only transcript/configuration and evidence health to OpenAI, never recording audio/video, signed URLs, Employee data or a candidate profile. The report is not a hiring recommendation, suitability score or personality/protected-trait analysis. Approximate recording correspondence is derived from verified unit intervals; missing correspondence remains explicit. Citation validation proves source membership, not the truth of a model interpretation. Managers must check source text and recording.

The application review workspace keeps summary, topics, scenarios, follow-up, transcript, recordings and decisions together. Findings navigate to a source turn and approximate playback context. Historical attempts remain selectable, including reports from earlier invitations. Recording health is collection evidence, not candidate performance. Reviewed reports are never silently replaced.

## Manager decisions and canonical Hire

`decision_state` is separate from candidate preparation and interview status. Allowed manager transitions are Review → Shortlisted → Final Interview, Shortlisted/Final Interview → Hired, and any non-terminal decision state → Rejected. Hired and Rejected are terminal. `recruitment_decide` validates active Admin identity, `recruitment.manage`, opening scope, expected state and a request fingerprint, then records append-only actor/reason/report evidence. AI functions cannot execute that authenticated command. Terminal decisions revoke outstanding invitation authority and prevent another invitation. An unfinished active interview must be ended before a decision.

Hire also requires canonical `employees.create` and `employees.view`, employee workplace access, confirmed person/contact/nationality/employment type/start fields, and active opening Position, Workplace and Legal Employer. The current Hire command converts into active employment with a Joined Date on or before today; future starters remain in the applicant lifecycle until employment begins. The conversion locks the application and applicant, serializes Recruitment person matching, and rejects existing IC/passport or normalized contact matches. Same-name ambiguity requires a recorded explanation; it does not silently merge people. One immutable `recruitment_hire_conversions` link per applicant and per Employee prevents duplicate conversions across openings. Identical request/actor/payload retries return the original Employee; changed retries and duplicate Hire are rejected.

The trusted adapter inserts one canonical `employees` record using the same table, auth-derived actor trigger, initial current-only employment-assignment baseline and workplace mirror triggers as ordinary People creation. It derives Position, Department, Workplace and Legal Employer from canonical opening masters. It creates no Recruitment employee representation, Auth login, role assignment or Crew credential. Joined Date does not fabricate historical employment evidence. The resulting Employee link opens `/people/employees?employee=<id>`; the existing scoped People profile, employment timeline and access/onboarding workflows own remaining setup.

## V1 launch readiness

Live recovery has a finite, cancellable Recruitment-owned operation with explicit Resumed, Recovery Required and Terminal outcomes. Resume activates fresh Web Audio and starts camera/microphone acquisition directly from the candidate tap. Suspended context close, stale uploads and local transcript retries do not gate continuation; local pending evidence stays disclosed while server-durable conversation/configuration/coverage remains the resume authority. Cold refresh reconstructs ownership from durable server state and exposes a bounded bootstrap retry. Idempotent recovery request results and expected-current recovery identity fence stale pause, capture-open, provider context and connected acknowledgements. Setup has a bounded 90-second lease before ordinary active heartbeat behavior. Native/media/server timeouts lead to visible retry or terminal explanation, never an indefinitely latched Resume/loading state. Bounded token-authorized operational diagnostics cover commands, visibility, stage/error/state, opaque tab comparison and track/audio states without raw identity, credentials or interview content. Both physical acceptance failures remain preserved; technical fault injections are not physical-device certification.

Approved V1 product consent is configured as a new immutable version; historical provisional evidence is retained. Admin distinguishes approved-copy readiness from pending real-device acceptance. The existing public surface has no Privacy Notice link/destination, so no policy content or URL was invented. Staging uses its canonical `/i/<token>` path while the future `interview.feedx.my` production domain awaits separate configuration after acceptance. The first human acceptance failed conversation continuity and recovery. Scoped fixes require renewed physical-device acceptance; no Production readiness follows from synthetic recovery tests. Phase 2 physical mobile limits and full human voice/interview acceptance remain pending; configured consent alone does not certify launch quality. See [Staging human acceptance guide](../../qa/recruitment/v1HumanAcceptance.md).
