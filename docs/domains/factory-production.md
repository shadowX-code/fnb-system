# Factory Production

## Purpose And Scope

This domain owns Factory Production Planning, Production Overview, Job Orders, production execution, batches, Batch Traceability, and read-only MeSTI Finished Product Storage Control and Food Processing Control projections.

## Canonical Ownership

Current Factory production pages/services, migrations, RPCs, RLS, route contracts, and tests are authoritative.
Current implementation overrides historical refactor-phase assumptions.
Factory Warehouse owns physical raw and finished-goods movement.
Factory Master Data owns recipes/BOM, production SOP, and factory reference data.

## Core Entities

- Production plans, planned quantities, dates, and status
- Job Orders and their material/product requirements
- Production runs, execution steps, consumption, output, yield, and exceptions
- Equipment bindings pinned by the Production SOP and applied at production completion
- Batches, lot references, lineage, quality/traceability evidence, and linked SOP/version context
- Production overview and reporting read models

## Lifecycle And Business Rules

Planning establishes intended production and may create or feed Job Orders through current controlled workflows.
Job Orders move through defined preparation, release, execution, completion, and exception states.
The server owns protected quantity calculations, state transitions, material validation, output posting coordination, and traceability links.

Execution pins the product recipe/BOM and SOP/version context needed to preserve historical meaning.
Recipe requirement scaling starts from the saved recipe quantity and `recipe_usage_uom`, then uses the declared Raw Material conversion path to calculate the Raw Material storage UOM. Batch allocation and stock deduction use only that storage UOM. Operational material quantities are rounded to four decimal places at that boundary; the preview, allocation, variance, and trusted completion authority use the same value. The completion authority repeats the standard-usage conversion for recipe-linked completions and rejects a missing or mismatched conversion rather than accepting a client-calculated substitute.
Finished Goods output is pinned to the Job Order Packaging SKU's canonical `storage_location_id`. Completion requires that exact Location to be active and storage-enabled; it does not infer or substitute a destination from a Storage method label such as Freezer.
Completed production and batch evidence is immutable except through explicit correction or reversal contracts.
Production SOPs bind the canonical active Factory Equipment instances required by the controlled process. On completed production, the trusted completion authority creates idempotent After Production Cleaning evidence for each bound Equipment using the `production_id + equipment_id` identity. The occurrence date is the Production `end_date` under the Malaysia operational-date contract; `completed_at` remains audit metadata. The occurrence freezes equipment, Location, batch, product, job order, SOP, and completion context so later master-data changes do not rewrite historical meaning.
Production Overview is a read model and does not own underlying lifecycle writes.

## Permissions, Snapshots, And Audit

Admin access requires production permissions and applicable factory/storage scope.
Protected transitions validate the caller and current state server-side.
Released/completed orders, pinned master-data versions, material consumption, outputs, exceptions, and batch lineage retain auditable evidence.
Factory staff/operator/responsible-person selectors use the People-owned active `workplace = Factory` population when the selection semantically requires Factory workforce. Factory role permissions authorize Factory functionality but do not make Management or Restaurant employees Factory workforce.

## Workflows And Integrations

Planners create and sequence production demand.
Operators or authorized supervisors release and execute Job Orders, record required evidence, and complete production.
Factory Master Data supplies products, BOM, SOP, suppliers/customers, and storage references.
Factory Warehouse validates and posts raw consumption, finished-goods receipt, movement, and dispatch context through established boundaries.

## Compatibility And Deferred Scope

Production Planning, Overview, Job Orders, Production, Batch Traceability, and Finished Product Storage Control are surfaces of this domain, not separate domains. Finished Product Storage Control is read-only: it projects exactly one canonical Finished Goods batch balance for each completed Production and does not create a MeSTI ledger or inventory movement. Batch Traceability projects persisted Production Raw Material batch allocations with their receiving, supplier, and storage provenance; it never reconstructs historical usage from recipes or inventory, and explicitly reports unavailable allocation evidence for older production records.

Factory List UI Foundation V1 begins with Batch Traceability. Its shared filter rail, compact table treatment, status badge mapping, date display helper, row-action cluster, pagination, list states, and composable semantic table cells are presentation-only primitives: they must preserve each listing's existing query, service, permission, and detail authority contracts. List composition is `Page Header -> optional Summary -> optional view tabs -> Filter Bar -> active filter chips -> table -> pagination`; filter controls keep content-aware widths and whitespace rather than stretching. Keep up to three useful criteria inline when they fit comfortably; use the shared compact Filters popover only for lower-frequency criteria. Row actions keep lifecycle mutations visible, use the Eye icon for read-only detail, and place edit/archive/cancel/delete in an overflow menu only when such actions exist. Semantic cells supply consistent primary/secondary hierarchy, entity/date treatment, semantic dot text, soft labels, attention values, progress counts, and muted states; pages remain responsible for mapping their domain state to a semantic tone. The primitives resolve all surfaces, controls, table states, and floating layers through FeedX theme tokens in light and dark modes. Other Factory pages adopt the foundation only through deliberate follow-up migrations.

Completed Production records move to `awaiting_verification` and can be verified only through `factory_verify_production_record`. Role Settings permission `factory_production.verify` is the canonical verification authority, verification is idempotent, and it does not alter saved Production or QC evidence. Food Processing Control projects completed Production, canonical output and expiry fields, and the completion and verification audit actors without creating a second processing or QC ledger. Its QC status is derived from the exact SOP version pinned to the Production: an SOP with no QC points is `No QC Required`; `Evidence unavailable` is reserved for a pinned SOP that required QC but whose expected evidence cannot be resolved.
Legacy plans may explain migration history but do not override active routes or contracts.
Machine telemetry, advanced finite-capacity scheduling, and external MES integration are deferred unless explicitly introduced.
# Operational completion attribution

Completed Production is attributed to its recorded `end_date` and `end_time` in `Asia/Kuala_Lumpur`. `completed_at` remains audit metadata for when the completion was recorded, and is not used for operational daily or monthly reporting.

## Monthly Production Performance

Production Overview consumes the read-only, RLS-preserving `factory_get_production_monthly_performance(date)` projection with `factory_production.view` authority. It uses the canonical operational completion function, never Planning quantities or audit timestamps. A completed Job Order counts once (the latest completed Production record if legacy replay rows exist). Actual output uses the canonical actual-output field precedence; only mass units (kg or converted g) contribute to kg totals, never packs or assumed litre density.

Productivity is eligible actual kg divided by summed valid recorded JO-hours from Production start to end. Missing, zero or negative durations are excluded along with their output from this ratio; the monthly ratio is weighted by summed hours, not averaged daily ratios. Overlapping JO durations remain JO-hours, not factory operating hours, OEE or target efficiency.

The trend averages the latest seven days with completed production, carrying up to six prior production days across month boundaries. Limited history uses the available days; a window with unresolved output is unavailable. Past dates without production are zero, future dates are unmeasured, and missing output is explicitly incomplete. Records without a complete Production End are disclosed as unattributed historical runs and are not assigned an invented date. Existing operational KPIs, pipeline and Recent Activity are independent and unchanged.

All three chart modes open the same Daily Production drill-down. The selected date and three daily KPIs stay above the contributing runs, which appear in a compact table or stacked rows on narrow screens. Each run shows its saved Production Batch No., Job Order No., canonical output, recorded pack quantity and valid JO duration. The monthly snapshot retains the source timestamps, and View opens them in the existing completed Job Order result. Detail identity joins retain source-table RLS; the projection does not elevate access or recalculate dates in the client. Closing detail preserves the selected month and chart mode, and existing completed Job Order result navigation remains the detail owner.

The monthly Dashboard operational wrapper materializes its inherited base analytics snapshot once per call before projecting operational completion overlays. It remains a security-invoker read under source RLS, with the existing permission checks, reporting definitions and Malaysia-time attribution. Reusing the snapshot avoids repeated analytics evaluation; it does not cache data across calls or extend API timeouts.

### Production identifiers

The database assigns new Production batches as `PBYYMMDD-NN` from the saved Production start date, using the Malaysia business date if no date is supplied. The sequence starts at `01` for each date and can exceed two digits. Existing saved values are authoritative. Job Order No. identifies the work order. Production links use `factory_productions.id` through the associated UUID fields. Missing batch associations appear explicitly, and printing continues to use pinned batch snapshots.

Admin and Gateway completion share the same writer and batch trigger. The writer stores no new `production_no` and posts the saved Batch No. with the Production UUID on stock movements and batch provenance. Gateway/MCP labels and operational evidence resolve by UUID and show the saved Batch No. Historical PRD text and audit evidence remain stored. The one-time migration can fill missing UUID relationships only when the historical reference and available batch or usage evidence agree. Existing UUIDs and saved batch numbers are preserved. Live movement and traceability reads never join on PRD, and unresolved relationships remain explicit.

## External Agent read projections

Navigation-scoped agents can inspect saved execution/QC/material records and the canonical operational pipeline through the Gateway. The pipeline and Planning open-order aggregate share their existing read authority with Admin and never call due-release or other mutations. Completed-production MeSTI projections reuse the canonical QC requirement/evidence status and batch quantity/UOM/date authorities with personal fields removed. Pinned-SOP or ambiguous batch gaps remain unavailable. Production Reports exposes permission-gated source records; current UI costing/yield calculations are not copied into a competing backend calculation. Gateway policy and scope are owned by `../architecture/trusted-authorities.md`.

## Factory Label Printing (Staging)

Job Orders and Completed pipeline cards expose Print Labels for completed batches. In Progress Job Order process details offer preview only, with placeholders for unconfirmed values. Queueing requires a completed batch and confirmed evidence. A batch identifies one authoritative Packaging SKU. Operators enter the number of copies for each submission. Print Labels suggests the remaining allowance from confirmed packaged units or verified cartons selected in Print Labels. Carton counts require operator confirmation against actual packaging evidence and an audit reason. The first submission freezes the evidence and limit for that label configuration and batch. Previously activated carton and single-batch limits still apply. Target output never enters quantity calculations. Label printing leaves Production, the Job Order lifecycle, packaged output and stock unchanged. Missing manufacturing/end date, expiry, batch or packaged quantity requires explicit confirmation and an evidence reason, saved only with the label. Recorded facts cannot be overridden. Production expiry wins over later label shelf-life settings; an approved label rule applies only when recorded expiry is absent.

The first queued label freezes one `factory_label_snapshots` record per Production batch and label configuration, approved SKU label content/configuration, exact assigned template version, canonical product-family defaults with label-only display overrides and the recorded Production title retained as provenance, dates, batch, quantity authority and confirmation provenance. The initial monochrome raster is reused for subsequent original labels and reprints, so browser fonts/master changes cannot rewrite history. Every original allocation consumes that label configuration’s batch allowance even after failure; recovery is an explicit reprint. Request fingerprints, per-batch locking and stable request IDs prevent duplicate submissions and over-allocation. The browser retains unresolved submission intent per operator/Job Order for retry across modal close/reload.

`factory_label_context`, `factory_label_enqueue`, `factory_label_claim`, `factory_label_report`, and `factory_label_resolve` are trusted authorities. Tables have RLS, no client table grants, and immutable template/config/snapshot/event evidence. View requires Job Order and Production view permissions; print uses `factory_production.complete`; reprint and physical confirmation/recovery use `factory_production.verify`. Actors are derived from active canonical employee/Auth links. No new production authority or role-assignment mutation is introduced.

States are Queued → Printing → Sent / Failed / Unknown. Confirmed is a supervisor's recorded physical inspection, never transport acceptance. Exclusive 10-minute claims serialize each device; expired claims become Unknown. Unknown blocks further device claims pending review. Native errors and interrupted submissions are held for inspection, never automatically resent. Sent may proceed through the bridge, but remains unconfirmed physical output. A controlled reprint references the original job, preserves its pixels, and records the reason and new quantity. Print History suggests the missing count after a reported issue and requires an explicit quantity after full confirmation. Queued work may be cancelled to Failed; live Printing cannot be cancelled. After queueing, Print Labels follows the submitted job by ID independently of paged history. Queue Labels submits the selected quantity and current validated preview directly. The selected bridge’s oldest Unknown takes priority in the Needs Review panel, including holds from another Job Order. Expandable Print History retains the audit and transport evidence without repeating that print’s recovery actions. An authorized verifier chooses Confirm Printed after checking the full count, or Report Issue after counting usable labels and clearing held output. Full confirmation records the requested count as usable after an explicit inspection acknowledgement. Issue reporting records the actual usable count, including zero, and a reason after the verifier clears any held output. The resolution RPC validates the count and records it in the immutable event. The printer picker identifies the Job Order and batch blocking a device. Sent and Unknown sources require resolution before a separate reprint can be queued. Append-only print events retain server timestamps and actors.

The Windows 10/11 per-user background bridge uses outbound HTTPS with normal Supabase Auth, active employee/permission checks on each RPC, DPAPI session/journal custody and a single-instance mutex. Driver/GDI spooler is the default. Both Windows transports require an installed print queue. RAW bitmap TSPL also requires verified command compatibility. The first D520 Windows acceptance uses the vendor USB driver queue. A D520 visible only in Windows Bluetooth settings or Labelife cannot be selected by the Windows Bridge. No Labelife dependency, cloud printer commands, inbound listener or service key is used. The installer, local calibration, offline handling and D520 limitations are documented in [`tools/windows-print-bridge/README.md`](../../tools/windows-print-bridge/README.md). Bridge registration/printer inventory/status is in `factory_label_devices`; it authenticates as its registering operator, and existing employee access controls revoke that authority.

The macOS bridge uses the same registration, employee authentication, frozen 203 DPI raster, claims and outcomes. It stores sessions in macOS Keychain and journals submission locally before sending to a configured CUPS queue or the D520 Bluetooth Classic SPP adapter, which selects the standard SDP service class and requires firmware bitmap mode 4. Label Management → Printers displays the reported connection and availability. D520 polarity and feed-direction correction live in the Bluetooth adapter. A completed Bluetooth write without a positive submission acknowledgment remains Unknown. Local single-label and three-label calibration use the same submission path without creating a Job Order label job. Setup, physical acceptance and recovery are documented in [the macOS bridge guide](../../tools/macos-print-bridge/README.md).

The web feature and bridge endpoint are restricted to the exact Staging Supabase project. Hardware acceptance on the macOS D520 Classic SPP path covered one calibration label, one S9 sample and three consecutive S9 samples on 80 × 90 mm stock. Reliable automatic physical completion remains unverified. Windows driver and physical output, barcode/QR scan acceptance, and physical paper-out recovery remain separate checks.

Printer Setup lives in Label Management → Printers. The guided native package opens from FeedX or the local app launcher. The setup app loads only the public Staging client configuration over HTTPS and signs in the original operator through the existing FeedX Auth service. The existing owner check controls registration. The app stores its session separately in Keychain or DPAPI and keeps the existing per-user device identity, calibration and recovery data across binary upgrades. macOS starts through a LaunchAgent registered when the setup app closes for an existing authorized registration, including older command-line registrations. A macOS Connection Check waits for a fresh report from the running LaunchAgent. Setup does not open a second printer channel or pause the worker for this check. The worker publishes its cloud heartbeat independently of the D520 probe schedule. Healthy D520 probes are spaced at least 60 seconds apart. Failed probes back off from 15 to 30 to 60 seconds. Connection Check requests an earlier probe through the same worker. Availability reflects the last timestamped check and expires after 90 seconds independently of saved calibration. Windows starts through a per-user scheduled task. Returning devices can reconnect using their saved configuration and calibration. Session-store read failures and network outages use bounded backoff; refreshed sessions must persist before any print claim or receipt processing continues. Pending journals retain their claim identity through recovery. Connection checks never submit print data. Local calibration asks for explicit copy-count approval and separately records physical inspection. The Web read model reports heartbeat, connection, calibration and job holds independently. The existing claims, immutable print evidence and recovery authority govern ordinary Job Order labels.

Label setup is centralized under Factory Settings → Label Management. Draft edits and shared-template activation leave operational printing unchanged. Unsnapshotted labels consume the active SKU configuration and its pinned template version. Read-only MFG, EXP, batch and actual packaged quantities remain Production-owned.

### External Agent lifecycle actions

The fixed Gateway action manifest exposes Job Order Create/Update, Submit (canonical Release), and pre-start Cancel; Production Update records QC progress, Complete consumes canonical batch allocations, and Verify uses the existing verification authority. These delegate to the same private business bodies as human RPCs. The physical operator remains the existing canonical Employee evidence, distinct from the machine recorder. QC/completion/verification require exact human evidence confirmation; an Agent cannot review its own linked Job Order/Production work, even after key replacement. No new Production start/cancel/approval lifecycle is invented. See Trusted Authorities → Factory operational actions for grants, retry receipts and concurrency.
