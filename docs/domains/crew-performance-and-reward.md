# Crew Performance And Reward

## Google Reviews Foundation

Google Reviews is a separate Admin reputation workspace under Performance. It owns future Google Business Profile connection, verified account/location discovery, explicit outlet-to-location mapping, and outlet/month review evidence. Customer Feedback remains a distinct first-party domain and never supplies Performance Customer points. Customer stays pending until verified Google evidence exists, which blocks Performance finalization.

### Phase 1 Reputation Integration

Phase 1 uses the existing Google Reviews workspace for an outlet-scoped, read-only Review Inbox. It is separate from first-party Customer Feedback and from the dormant Google-to-Performance scoring adapter below. The Phase 1 read/sync core does not publish replies, generate AI responses, aggregate review ratings into employee metrics, finalize Performance, or consume Reward authority. Explicit owner-reply management is the separately governed Phase 2 extension below. Existing monthly target configuration/audit and Performance authority are preserved, but target controls are not shown in normal Google Reviews Settings while scoring is disabled.

The `google-business` Edge Function verifies Admin Auth with `getUser`, then delegates to the service-only `crew_google_business_server` authority. The authority reuses canonical role/permission/outlet helpers for the verified Auth identity. Reading or syncing an inbox requires `crew_performance.view` and access to its active outlet. Managing the shared connection, rediscovering accounts/locations, disconnecting, and mapping requires `crew_performance.review` plus all-outlet access. Scoped readers never receive the global account/location inventory. Locations are mapped explicitly, uniquely, by full `accounts/{account}/locations/{location}` resource identity; titles never determine ownership.

The fixed Staging HTTPS callback is `https://ujkzdaaadnvcfayuldmh.supabase.co/functions/v1/google-business/callback`. It reuses the existing FeedX Business Profile OAuth client and requests only `business.manage`, with offline consent, expiring one-time state and S256 PKCE. Credentials are held in `GOOGLE_BUSINESS_CLIENT_ID`, `GOOGLE_BUSINESS_CLIENT_SECRET` and `GOOGLE_BUSINESS_TOKEN_ENCRYPTION_KEY`; an optional previous encryption key supports controlled rotation. Tokens/verifiers use the shared AES-GCM server credential helpers, bound to connection generation, in a private schema inaccessible to browser roles. Refresh uses compare-and-swap so concurrent requests cannot overwrite newer credentials. Reconnect advances generation and invalidates cached reviews. Disconnect immediately disables local access and clears the cache, then revokes the Google grant; failed revocation remains retryable and cannot restore local access.

Sync performs GET-only account/location/review reads. Review pages are walked to completion before an atomic encrypted cache replacement. Identity deduplication preserves original creation time, review updates, authored comment/rating and existing owner reply/timestamp; foreign identities, repeated pages and conflicting revisions fail closed. A sync lease and connection/mapping revision guards reject concurrent or obsolete work. Partial/failed syncs never appear complete. Explicit location rediscovery refreshes the access token before checking provider access. A 429 is surfaced with the exact API host/request and is not automatically retried.

Review content is a secure performance cache with a 24-hour read expiry and independent hourly purge, not permanent employee evidence. Raw content is not scored or stored as aggregated metrics. Google account/location discovery labels expire within 30 days; explicit outlet/resource mapping and FeedX configuration audit are retained separately. The inbox attributes Google as the source, displays original content/replies and source identity, and offers rating, owner-reply, text, creation-month and ordering filters. The browser neither persists content nor receives provider tokens. The location-wide Rating Overview prefers the official Google average/count retained unchanged with the same complete encrypted sync snapshot; legacy complete snapshots without those fields show a clearly labelled Synced Reviews Average. Per-rating counts/bars are transient display projections of the entire unfiltered location snapshot, never persisted metrics or employee scoring inputs. Missing, failed, count-mismatched or expired evidence shows unavailable values; a complete empty snapshot has zero reviews and no numeric average. Individual ratings use only their actual count of filled stars. Review Inbox and Settings share one workspace. Settings shows a compact connection summary with secondary management actions and confirmed disconnect, plus a multi-outlet mapping table assembled through the existing outlet-scoped context reads. Mapping edits explicitly choose or remove a verified location using the canonical generation/revision-checked authority; failed reads are unavailable, never assumed unmapped, and changed mappings invalidate prior review content.

### Phase 2 Owner Reply Management

Review Detail is part of the same Inbox, not another page. Fresh review/reply reads use the mapped Google resource and retain moderation evidence. Reply text is authored without automatic translation and is limited to Google's 4096 UTF-8 bytes. An explicit Publish Reply/Update Reply confirmation submits intent through the existing encrypted OAuth grant and the official `reviews.updateReply` PUT. The existing `crew_performance.review` permission plus canonical selected-outlet access owns reply management; it does not grant all-outlet connection/mapping management. View-only Admin can open detail but cannot publish.

Service-only reply RPCs store a fingerprint-bound request ID, server-derived actor/time, and a per-review lease. The final write guard revalidates permission, connection generation, mapping revision, resource and active lease immediately before PUT. Google writes are never automatically retried. A lost response is reconciled by reading the remote reply; an identical desired reply confirms the original intent without another PUT, while another author's changed reply requires explicit reload/review. An uncertain intent prevents competing publications. Check Status is read/reconciliation only. Replay of a confirmed intent has no provider write or duplicate audit event.

API acceptance is distinct from public moderation: pending/rejected Google states remain visible. Attempt/outcome events retain actor, operation, source identity and remote fingerprint/timestamp; temporary raw intent/reply material is encrypted and purged after 24 hours, while non-content audit metadata remains. Confirmed outcomes patch only the exact complete canonical cache snapshot without extending its expiry or changing rating evidence; otherwise they invalidate stale/concurrent cache work and use the existing sync authority. Drafts remain visible on failure, and feedback lives in the sticky shared modal footer. No first-party Customer Feedback, AI publishing, Performance scoring or Reward authority is involved.

Implementation verification uses synthetic transport responses and transaction-rolled-back Staging authority fixtures. Real Google publication/editing requires separate explicit approval; a Staging deployment is not that approval. See [Owner reply verification](../testing/google-business-owner-replies.md).

Setup and Staging verification: [Google Business Profile Phase 1](../testing/google-business-profile-phase-one.md).

The outlet/month Admin context is permission- and outlet-scoped. While GBP API access is pending, new/positive/negative reviews, average rating, negative rate, trend, breakdown, feed, and Customer points are unavailable rather than zero. No Google review text, reviewer identity, rating, or derived scoring evidence is stored. Connection and location mapping controls remain unavailable until a server-side provider adapter can obtain verified accounts and locations. Credentials must remain server-side; browser code must never receive OAuth tokens. The configuration tables hold only connection status, verified location resource names, outlet mapping, and targets, with no review payloads.

An authorized Performance reviewer may set a positive monthly target greater than zero for an accessible outlet and whole performance month. Each change records the previous/new value, actor, and server time. Once any Performance result for that outlet/month is finalized, the target is locked. Provider data must eventually use each review's creation time to assign its month, classify 4–5 stars as positive, 3 as neutral, and 1–2 as negative. The future Customer contract has Positive Target `min(positive reviews / monthly target, 1) × 15` and Quality up to 5 from the current-month negative rate (negative reviews / eligible reviews): at most 2% → 5, >2–5% → 4, >5–10% → 3, >10–15% → 2, >15–20% → 1, >20% → 0. Neither calculation is enabled before the live Google authority is approved. Future integration must resolve Google retention/policy requirements and snapshot finalized evidence.

## Pre-API Google Boundary

The server-only `googleReviewsContract.ts` adapter is dormant: it has no OAuth handler, network implementation, persistence, scheduled job, or Performance/Reward caller. Account and location discovery are paged contracts; mappings must use verified provider resource identities. Review reconciliation walks every page, rejects partial/repeated pagination and foreign-location identities, deduplicates external review identity by update time, and preserves immutable creation time. Malaysia-local creation month determines eligibility; update dates and cumulative Google totals never define the performance month. Each complete reconciliation starts fresh rather than carrying forward removed reviews.

The unconnected scoring preview is tested against the approved 15-point target and 5-point quality thresholds, but is not an operational scoring authority. A complete reconciliation with zero eligible reviews keeps Customer Pending because there is no negative-rate denominator. Missing/partial evidence also remains Pending, never an employee penalty or finalized score. The V2 framework is active; Google-dependent finalization and Reward consumption remain blocked.

Google Reviews presentation distinguishes API pending, disconnected, unmapped, awaiting reconciliation, syncing, connection/sync failure, complete empty, available and finalized evidence. Metrics/feed require complete evidence; fixtures exist only in tests. Target history is a separate authenticated, permission/outlet/month-scoped configuration read (`crew_google_target_history`); it exposes prior/new targets and server timestamps, not credentials or raw actor identifiers. The existing target-write/finalization lock is unchanged.

The live gate requires API approval, authorized OAuth/account/location discovery, confirmed mappings, real pagination and reconciliation, and validation against real evidence. Separately, Google policy approval must establish whether aggregation and durable finalized Google-derived snapshots are permitted: current GBP policies restrict stored API content to 30 days and prohibit aggregation/manipulation of stored content. Do not activate scoring or add durable Google evidence retention merely because API access is granted. Provider credentials stay server-side and all live capability gates remain disabled until these requirements are resolved.

See [Google Business Profile policies](https://developers.google.com/my-business/content/policies) and [review-list API](https://developers.google.com/my-business/reference/rest/v4/accounts.locations.reviews/list).

## Lifecycle And Business Rules

Monthly Performance uses defined, private evidence adapters rather than reading mutable page state.

Current Performance is Service Crew only and has one scoring model, `performance-v2`: Attendance 30, Service 30, Customer 20, Knowledge 15, and Team Review 5. `calculation_version` records that model but does not select a legacy runtime branch or require a start-month switch. Attendance, Service, and Knowledge reuse their canonical authorities. Team Review owns coworker eligibility, review evidence and moderation; Performance consumes only its Ready monthly `/5` result. Customer is explicitly pending until a separate Google Review authority is approved and delivered; FeedX Customer Feedback is never its fallback. While Customer is pending, `total_score` stays null, finalization is rejected, and Reward cannot consume provisional earned points. Historical applied migrations remain in repository/database lineage even though obsolete V1 operational evidence was retired by a forward-only cutover.

Open monthly Performance now resolves Service Crew eligibility, Position, Employment Status, Employment Type and Workplace through the People Employment Assignment Timeline for the performance period. A verified assignment from another month, today's Employee projection, and current Crew Access are not historical substitutes. The Performance adapter reads Team Review evidence for that resolved period outlet while Team Review retains its own submission and workflow authority. The single-outlet monthly scoring model cannot safely represent a material intra-month assignment change, so such periods require review rather than using month-end identity. Before the verified People cutover, missing assignment history also remains unresolved. Open result components pin the applicable People revision IDs and assignment; a later historical correction masks stale scores until an authorized reviewer explicitly recalculates with a reason and audit entry. Source Team Review, Customer Feedback, Attendance, Knowledge and Service evidence is retained. Finalized results remain pinned and are never refreshed from later People changes. Crew receives the safe period-correct result without resolver internals or stale open-score trends.

Team Review lifecycle and evidence rules live in [Crew Team Review](crew-team-review.md). The internal Performance `peer` component key and `peer_score` column remain compatible storage identifiers, not current product terminology or an alternative review authority. Provisional Team Review points are withheld from Performance; only Ready evidence is consumed.

Attendance contributes a server-derived 30-point component: 15 points for completed eligible published shifts and 15 points for punctuality. Clock-ins at most 600 seconds after shift start receive no punctuality deduction; more than 600 through 1200 seconds deduct 0.5 points, more than 1200 through 2700 deduct 1.5 points, and more than 2700 deduct 3 points per eligible completed shift, with punctuality never below zero. No completed eligible evidence leaves the affected half at its neutral 12/15 baseline. Approved leave, non-working roster entries, schedules published or updated after their shift start, and reasoned active Attendance Performance exceptions are excluded. Finalized Performance snapshots remain immutable; only mutable current-period results refresh when attendance evidence changes.
The server derives protected scoring, eligibility, and reward values from canonical evidence and configured rules.
Reviewers may add permitted assessment evidence or decisions but cannot rewrite source-domain history.
Current mutable Service Standards reviews contain Welcome / Greeting, Thank You / Goodbye, Grooming, Work Area Cleanliness, and Guest Interaction. The server requires that exact current set and derives the observed-criterion denominator. Conduct is not a current Performance component. A finalized Performance period rejects new review evidence and remains immutable.
Mutable Performance labels the provisional sum as assessed points, names pending components, and reserves `/100` and the performance band for finalized results. Neither display changes review readiness or finalization eligibility. The complete Performance total and finalized snapshot remain the authority for downstream Reward; Reward does not consume mutable assessed points.

Crew trend presentation is a read-only comparison only when the current month has a finalized score. Partial assessed points carry scored/pending component context without a `/100` label, performance band, or comparison to a finalized prior month. A shared presentation formatter rounds a valid comparison magnitude to at most one decimal, normalizes floating-point no-change residue to zero, and never changes the server score, period selection, or Reward authority.

Reward consumes only finalized Performance. A mutable Current Score, regardless of its value, remains `awaiting_performance` for Reward and cannot create a Reward entry, projection, payout snapshot, or campaign-state change. Finalized and paid Reward entries remain the sole authority for final or paid amounts and historical payout records.

A Reward Campaign is finalizable only after its frozen participant set has a current complete calculation and every participant has a legitimate final Reward outcome: `qualified` or a documented non-payout `not_eligible` result. Missing, uncomputed, malformed, or `awaiting_performance` entries are payout-critical blockers. The trusted finalization authority locks and evaluates this readiness atomically before any entry/cycle mutation; the scoped Admin read model exposes only a human-readable readiness projection for review. Existing finalized and paid Campaigns are immutable historical evidence.

Customer Feedback preserves each guest submission as independent evidence. It owns `crew`, `food`, and `outlet` scope: only Crew feedback is attributed to an employee and may be included or excluded through an audited server authority. Its existing `scoring_status` is retained for feedback moderation/reporting compatibility, but Customer Feedback no longer contributes to Performance Customer points or Reward. Food and outlet feedback remains unassigned. Crew attribution remains one-to-one in the current phase; corrections use canonical Crew identifiers and retain prior/new attribution and reason in append-only audit history. Finalized Performance and Reward outputs remain immutable.

Customer Feedback also owns trust protection and complaint context. Public feedback supplies a first-party opaque anonymous device identifier; the server stores only its hash and uses deterministic, privacy-bounded signals to flag suspicious Crew evidence as `review_required`. Trust state is independent of inclusion state; neither state changes V2 Performance. Trust decisions, exclusions, and follow-up status transitions are append-only audit events. Improvement feedback records an outlet-local approximate visit time and business date separately from submission time. Optional guest contact information is stored in a separate follow-up record, returned only to authorized Customer Feedback follow-up roles, and is never available to Crew Mobile, Performance, or Reward.

Public guest feedback uses an outlet-scoped opaque `public_feedback_token`, not an outlet UUID, at `/feedback/<token>`. Guests choose Crew Member, Food & Drinks, or Overall Visit before submitting experience, scope-specific canonical tags, and an optional comment. The public resolver returns only the outlet display name, an optional public outlet-logo reference, and eligible recent/on-shift Crew; token submission resolves the outlet server-side and applies scope validation, dedupe, request-hash, and evidence insert. A retained compatibility refresh function is a no-op for Performance. Outlet logos are outlet-owned media managed through the canonical Outlet editor with scoped Admin upload/replace/remove authority; public feedback may read only the active public asset reference. Legacy `#feedback?outlet=<uuid>` links remain supported and normalize to the token URL after resolution. Admin Customer Feedback provides the selected outlet's QR, stable public link, copy action, local QR download, and a scope-aware evidence table without creating a separate Admin page.

## Compatibility And Deferred Scope

Legacy Growth People, Performance Reviews, and Reward Cycle routes are compatibility entries into this domain.
Growth, Performance, and Reward remain one bounded domain because they share evidence-to-outcome lifecycles, while their state machines stay distinct.
Payroll disbursement, tax treatment, and external benefits integration are deferred unless current contracts introduce them.

Owner-reply read reconciliation retains the latest unexpired encrypted accepted PUT evidence only for the current outlet/resource, connection generation and mapping revision. Detail, Inbox and sync use the same projection: missing/older read-back cannot erase a newer confirmed reply. An identical reply text is reconciled even when Google GET truncates the PUT timestamp precision. A differing read-back shows the confirmed content with a pending reconciliation state and blocks another PUT until Google catches up; newer remote edits remain authoritative. Google GET failures remain errors, never evidence of reply absence. Drafts survive reload/failure; the 24-hour content expiry and audit metadata retention are unchanged.

Review Detail automatically reconciles confirmed replies through up to four read-only detail requests, with 2/6/12-second waits only after a successful-but-stale read. Matching authored text is reconciled despite Google timestamp precision differences. Errors (including 429) stop the read loop without automatic retry. The final feedback is either Reply synced (or Google's moderation state) or Sync pending with explicit Retry sync; accepted evidence/drafts remain visible and another write stays blocked while pending. Closing Detail prevents further retry requests. Existing write idempotency, audit, mapping and cache expiry authorities are unchanged.

Ordinary Google Business Profile Disconnect atomically clears only this environment’s encrypted connection/cache and does not revoke Google authorization. Dedicated Staging/Production OAuth clients and keys may share the approved Google project. Revoke Google Authorization is a separate confirmed action warning of same-account, project-wide impact across environments. Connection generation, Admin management permission and outlet scope are revalidated by the server. Fixed project/origin/callback allowlisting rejects unknown and cross-environment browser access.

## Google Reviews operational permissions and synchronization

Google Reviews registers six independent canonical grants under Performance: `crew_google_reviews.view`, `.sync`, `.publish_reply`, `.edit_reply`, `.manage_connection` and `.manage_mapping`. Actions depend on View and current authorized active outlet scope. Connection and mapping administration independently require all-outlet authority; neither follows from Publish/Edit or Sync. Existing Performance-backed Google access is migrated to equivalent explicit grants, retaining role assignments/outlet scope and recording the split. Roles without prior access gain none. Owner/Admin protected-role authority remains canonical. The role editor recognizes this outlet-scoped integration even though its navigation lives in Crew Performance.

Canonical Staging schedules `crew-google-business-review-sync` every 30 minutes through existing pg_cron/pg_net into the Google gateway. Dispatch creates a one-use, four-minute run capability whose hash and lease remain private; there is no new permanent worker credential. Duplicate dispatch/claim is rejected. The worker walks only explicit mappings for active outlets with a connected grant and uses the same complete pagination/deduplication, token refresh/CAS, per-location lease and generation/mapping guards as manual Sync Now. It never invokes reply writes. One transient read retry is allowed; 429 ends the run without retry and records exact service/request plus a 30-minute shared cooldown. Expired Google authorization pauses the run; location-specific permission failures are recorded without blocking other mappings; manual sync retains its separate permission. Runs have a 105-second budget and process up to 32 mappings, oldest successful sync first.

Per-location metadata retains last attempt, successful sync, failure and sanitized provider error separately from the 24-hour encrypted content cache. Expired/partial caches never become official rating evidence; changing connection generation or mapping hides prior sync metadata/content. Inbox shows automatic cadence, last success and one actionable failure next to Sync Now, and polls only FeedX's stored context while visible. OAuth, global-revocation separation, owner-reply audit/idempotency, cache purge, first-party Feedback and disabled Performance scoring remain unchanged. The scheduler dispatch URL is intentionally Staging-only; Production scheduling requires a separately approved environment-compatible migration.
