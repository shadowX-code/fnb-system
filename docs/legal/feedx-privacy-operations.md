## Durable erasure and restore contract

- `marketing_privacy_prepare_meta` derives exact authorizer/grant scope from canonical Meta subjects. `marketing_privacy_prepare_customer` requires the restricted privacy operator's independently verified identity evidence and exact organization/brand/conversation. A sender is never equated with an OAuth administrator.
- Intents contain only protected hashes, opaque conversation/connection IDs, grant generations, cutoff timestamps, opt-out flags, minimal hold proof and scoped temporary OAuth session IDs. No names, message/AI text, access tokens, authorization codes or app secrets. These are **pseudonymous** records, not public or anonymous data.
- AES-GCM binds each object to Staging and its event ID. Separate server-only `MARKETING_ERASURE_JOURNAL_ENCRYPTION_KEY` is independent of Meta token rotation. The server-only `MARKETING_ERASURE_JOURNAL_READ_WRITE_TOKEN` belongs to this private store. Keep recoverable encryption keys in the approved secret custody process; retain old keys until their journal objects can be verified/re-encrypted. Losing keys makes replay unavailable: quarantine remains required.
- Before canonical erasure, Edge writes an immutable object and decrypts/read-verifies its digest. Only then does the service acknowledge the receipt and execute existing erasure. Failed writes return an incomplete/retry response; the original data is not silently deleted without recovery evidence. The existing worker retries pending exports; it does not independently invent identity verification or send messages.
- Customer erasure: restricted `POST /functions/v1/marketing-privacy/erase-customer`. Legal-release evidence uses `/release-hold`, also durable before archive deletion. Both authenticate the existing private worker secret; never browser-accessible or an ordinary staff identity-attestation endpoint. `marketing_meta` retains official signed-callback verification and opaque public receipts.
- Restoring an environment is a **controlled operator workflow**, not something detected automatically by a database flag. Before any physical/logical restore, restrict application access, inbound webhooks, AI and workers using infrastructure controls outside the database restore boundary. Reapply forward migrations if the snapshot predates them; restore server secrets; do not run old deployed authorities. Do not restore or replace the independent journal store with the database.
- While quarantined, authorized operations invoke `POST /functions/v1/marketing-privacy/restore-replay` with `quarantineConfirmed:true`. The endpoint scans the independent Blob index, not a restored SQL manifest; validates/decrypts all evidence before mutations; replays chronologically through service-only `marketing_privacy_replay`; restores local receipt/suppression caches; removes restored Inbox/AI/derived FAQ/cache/webhook data and stale grant credentials/posts/jobs. Later authorization generations and internal cases remain separate. Released legal archives are erased again; documented ongoing holds remain restricted.
- Any corrupt/unreadable record, missing key, network failure, failed SQL replay or volume requiring operator batching keeps recovery incomplete. Partial replay is safe to retry. The response always reports `access_reopened:false`; infrastructure reopening requires operator review of exact scope, no resurrected records, execution gates and backup/export inventory. Never treat a `true` request flag as evidence that infrastructure access was actually restricted.
- Neither replay nor journal acknowledgment proves expiry of old snapshots or provider copies. Existing public receipts and `marketing_privacy_complete_followup` still require verified backup/processor evidence and resolved legal holds. No scheduled category purges were enabled.

The pre-erasure **logical snapshot of disposable rows only** was restored, including a stale credential and deleted messages; all SQL journal/case/tombstone caches for those fixtures were deliberately removed.

Assertions verified no restored bodies/AI/FAQ/cache/webhooks/released archive; restored opt-out evidence; stale credential removal; later grant/credential/post and internal case preservation. Repeat replay erased zero conversations and did not double usage totals. Recovery receipt caches were reconstructed. No full shared-project physical restore was performed; that destructive provider operation needs a separate change window. People bootstrap created one immutable assignment revision; its synthetic employee/empty role were deactivated instead of bypassing that domain guard. No real employee history was changed.
